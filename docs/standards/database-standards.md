# Database Standards

Binding conventions for **all** schema in this repository. Locked with the
user on **2026-07-22**. Every migration must comply from revision one —
retrofitting is the expensive path.

---

## 1. Scope & precedence

Applies to every table, column, constraint, and migration in Office-Connect.

**Precedence when sources disagree:**
user's standing rules → `docs/standards/` (this doc) →
module specs in `references/` → the `.docx` execution plan (scope/sequence).

> **Important:** the reference specs (`references/Reimbursement_Module_Build_Spec_v1.md`,
> the integration blueprint, the `.docx`) use **singular** table names
> (`reimb_claim`, `core_activity`) and abbreviated column sets. They are
> read-only historical source material and are **never edited**. On
> implementation every table name is **pluralized** per §2 and every table
> receives its mandatory column set per §6. Each divergence is recorded in the
> module's **delta register** (`docs/modules/<module>.md`). Do **not**
> "correct" plural names back to the spec's singular in a future session.

## 3. Keys

- **PK:** always `id BIGINT GENERATED BY DEFAULT AS IDENTITY`
  (`GENERATED ALWAYS` on hash-chained append-only tables so nobody can insert
  an explicit id into the chain). **No UUID PKs** — single-node on-prem
  Postgres, the audit hash chain needs a total order, and auditors cite
  human-legible numbers. External exposure is handled by reference numbers
  (§12) and authorization, never by obscure PKs.
- **FK column:** `<singular_referenced_noun>_id` → referenced table's `id`.
  `core_users.role_id → core_roles.id` · `reimb_claim_items.claim_id → reimb_claims.id`
- **Future FKs:** every `*_by` column (`created_by`, `updated_by`,
  `deleted_by`, `actor_id`) is a future FK to `core_users.id`; until
  `core_users` exists (Phase 2) they are plain nullable `BIGINT`. Same for
  `division_id` / `section_id` (org units, Phase 2). The FK constraints are
  added in one Phase-2 migration.
- **Polymorphic references** (`holder_kind` + `holder_id`) are the sanctioned
  exception to real FKs — document each use in the module doc.
- **No `ON DELETE CASCADE`** — deletes are soft (§8); cascade semantics are
  application logic.

## 4. Constraint & index naming

Enforced by the SQLAlchemy `naming_convention` on the shared `Base`
([`office_connect/core/base.py`](../../office_connect/core/base.py)) so
Alembic autogenerate emits deterministic names:

```python
NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

**Index every** status, holder, deadline, and FK column.

## 5. Enums vs lookup tables

- **Native PG enums** for closed, machine-owned sets (status machines,
  `kind` discriminators). Enum type name: `<module>_<subject>_<column>`
  singular, e.g. `core_activity_status`, `reimb_claim_kind`.
- **Lookup/catalog tables** for admin-editable sets (checklist catalogs,
  return-reason taxonomies). They carry `is_active` (§6) — deactivate,
  never delete.

## 6. Mandatory columns by table class

Every table belongs to exactly one class:

| Class | Columns | Examples |
|---|---|---|
| **Business** | `created_at timestamptz NOT NULL` · `created_by BIGINT NULL` · `updated_at timestamptz NOT NULL` · `updated_by BIGINT NULL` · `deleted_at timestamptz NULL` · `deleted_by BIGINT NULL` | `core_activities`, `reimb_claims`, `core_tenant_configs` |
| **Lookup / catalog** | all Business columns **plus** `is_active boolean NOT NULL DEFAULT true` | `core_feature_flags`, `reimb_checklist_catalogs`, `reimb_return_reason_catalogs` |
| **Append-only event** | `created_at` (+ `created_by` / `actor_id`) **only** — no `updated_*`, no `deleted_*`. Immutability is enforced by grants (§8), not columns. | `core_audit_logs`, `core_query_logs`, `reimb_status_histories`, `reimb_return_events`, `reimb_external_events` |

The append-only class is the **documented exception** to the
soft-delete-everywhere rule: `updated_*`/`deleted_*` columns on an immutable
event log would contradict the very auditability it provides.

## 7. Audit trail (standing rule 5)

Two layers, both mandatory:

1. **Row-level ownership columns** — the `created_by`/`updated_by`/`deleted_by`
   columns of §6 on every table.
2. **The hash-chained log** — `core_audit_logs`: append-only, one row per
   insert / update / soft-delete of any audited table, carrying
   `old_data`/`new_data` JSONB diffs, `prev_hash`, `row_hash` (SHA-256 chain,
   genesis `prev_hash = "0" * 64`). Populated automatically by SQLAlchemy
   session listeners ([`office_connect/core/audit.py`](../../office_connect/core/audit.py));
   `verify_chain()` recomputes the chain and is a Phase-0 QA gate
   (tamper attempt must be detected).

**What must produce an audit event:** every state transition, every waiver /
override, every config or flag change, every soft delete. The app DB role has
**no UPDATE/DELETE** on the log itself (§8).

> **Payload policy (flagged 2026-07-23, decision executes at Stage B —
> master plan §4 #4):** hash-chained payloads can never be redacted, so for
> tables carrying sensitive personal information the default policy is to log
> entity IDs and changed-**field names**, not sensitive values; display values
> resolve at read time. Rationale: RA 10173 vs immutable logs
> (`docs/research/round1/dpa-retention-audit-compliance.md`).

## 8. Soft deletes (standing rule 6)

- **Semantics:** `deleted_at IS NULL` = live row. Soft-deleting sets
  `deleted_at = now-UTC` and `deleted_by = actor`.
- **Default filtering:** a global ORM listener applies
  `deleted_at IS NULL` to every select of a soft-deletable entity
  ([`office_connect/core/soft_delete.py`](../../office_connect/core/soft_delete.py)).
  Escape hatch: `.execution_options(include_deleted=True)`.
  *Caveats:* raw `text()` / Core-table queries bypass the filter — query via
  ORM entities, or filter manually and say so in a comment; `session.get()`
  served from the identity map emits no SELECT and can return an
  already-loaded soft-deleted object — check `deleted_at` or use `select()`.
- **No delete-orphan cascades, no ORM bulk DML:** relationships never
  configure `delete-orphan` (a cascade delete would bypass audit — the
  listeners raise if one fires), and ORM-enabled bulk
  `session.execute(update()/delete())` is blocked because it bypasses the
  audit chain — load and mutate instances; maintenance scripts may pass
  `execution_options(allow_unaudited=True)` and must write audit rows
  themselves.
- **Uniqueness:** natural keys use **partial unique indexes** —
  `UNIQUE (...) WHERE deleted_at IS NULL` — so a soft-deleted row never
  blocks reuse of a name/key, **except** reference numbers (§12), which are
  never reused even after soft delete.
- **DB enforcement:** the app role (`oc_app`) has `SELECT/INSERT/UPDATE` on
  mutable tables, `SELECT/INSERT` only on append-only tables, and
  **no `DELETE`, no `TRUNCATE`, anywhere**. Migrations run as the privileged
  owner role (`oc_dev`). Hard deletes are physically impossible for the app.
- **Soft delete ≠ records disposition (codified 2026-07-23):** soft delete is
  a data-integrity mechanism only. Government records (claims, vouchers,
  tracked documents and their attachments) follow NAP/GRDS retention law:
  10-year retention for DV-supporting financial records counted from final
  settlement, `legal_hold` blocks, and **no automated purge ever** — disposal
  of public records without written NAP authority is a criminal offense
  (RA 9470). Modules holding records carry `retention_class` /
  `retention_starts_at` / `legal_hold` metadata and expose a
  disposal-eligibility report; destruction happens outside the system after a
  human NAP Form 3 process, and the DB rows remain (status change + audit
  entry only). See master plan §3.1.

## 9. Time

- Store **`timestamptz`, always UTC**. Naive datetimes are forbidden —
  `office_connect/core/time.py` (`ensure_aware()`) raises on them.
- `date` (no tz) for civil dates: trip dates, deadlines.
- Display **Asia/Manila**, converted at the edge via `core/time.py` only.

## 10. Money

- `numeric(12, 2)`, Philippine Peso.
- **All arithmetic server-side** — the UI displays, never computes.
- Display format: `₱2,200.00`.

## 11. JSONB

- **Allowed:** per-row `custom` extension bags; computed `totals` snapshots;
  rule grammars (`required_rule`, `auto_checks`); audit `old_data`/`new_data`.
- **Forbidden:** anything other modules must join on, filter by, or FK to —
  spine keys are always real columns.
- GIN-index JSONB columns that get queried.

## 12. Reference numbers

- Format `XX-YYYY-NNNN` (e.g. `RB-2026-0001`), `NNNN` resets yearly.
- Per-module prefix registry:

  | Ref prefix | Meaning |
  |---|---|
  | `RB` | Reimbursement claim |
  | `LQ` | Liquidation |
  | *(register future prefixes here)* |

- Generation via the pluggable per-module strategy (plan S-4). Gap-tolerant,
  but a number is **never reused** — not even when its row is soft-deleted.
- Unique via partial index `WHERE deleted_at IS NULL` **plus** the no-reuse
  guarantee from the generator.

## 13. Migration rules

- **One Alembic chain** for the whole platform; module tables live in the
  same chain with their prefixes.
- Upgrades must be **idempotent-safe**: `alembic upgrade head` twice in a row
  is a no-op the second time (Phase-0 QA gate).
- Every table is created with its **full mandatory column set** (§6) in the
  same revision that creates it.
- New **append-only** tables must explicitly `REVOKE UPDATE` from `oc_app` in
  their migration (default privileges grant it — see the note in
  `alembic/script.py.mako`).
- No destructive downgrades once real data exists (governance gate).

## 14. Canonical example

The copy-from template — every rule above applied to one business table:

```sql
CREATE TABLE reimb_claims (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY,
    ref_no        TEXT NOT NULL,                      -- RB-YYYY-NNNN (§12)
    claimant_id   BIGINT NULL,                        -- future FK → core_users.id (Phase 2)
    activity_id   BIGINT NULL REFERENCES core_activities (id),  -- spine key, nullable (soft reference)
    status        reimb_claim_status NOT NULL DEFAULT 'draft',  -- native enum (§5)
    total_amount  NUMERIC(12, 2) NOT NULL DEFAULT 0,  -- PHP, server-computed (§10)
    custom        JSONB NOT NULL DEFAULT '{}',        -- extension bag (§11)
    -- mandatory business-table columns (§6):
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(), -- UTC (§9)
    created_by    BIGINT NULL,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by    BIGINT NULL,
    deleted_at    TIMESTAMPTZ NULL,                   -- soft delete (§8)
    deleted_by    BIGINT NULL,
    CONSTRAINT pk_reimb_claims PRIMARY KEY (id)
);
CREATE UNIQUE INDEX uq_reimb_claims_ref_no
    ON reimb_claims (ref_no) WHERE deleted_at IS NULL;   -- partial unique (§8)
CREATE INDEX ix_reimb_claims_status ON reimb_claims (status);   -- index status cols (§4)
-- grants: SELECT/INSERT/UPDATE to oc_app — never DELETE (§8)
```
