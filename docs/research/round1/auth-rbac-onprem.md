# agent1
TOPIC: Auth + RBAC best practices for Office-Connect: an on-prem, same-origin internal government web app (FastAPI + PostgreSQL 16 + Redis, Windows Server production)

## KEY PRACTICES
- PRACTICE: Use server-side sessions (opaque ID in an HttpOnly cookie, session state in Redis) instead of JWTs for the browser app
  WHY: For a same-origin internal app there is no cross-domain/federation need that justifies JWTs. Server-side sessions give instant revocation (terminate an employee, force logout on incident), central visibility of active sessions, and no key-management or token-replay surface. OWASP guidance favors server-side sessions for sensitive/security-conscious apps (banks, government); JWTs' statelessness is precisely the property you do NOT want when HR says 'this person left today'. Redis is already in the stack, so this costs nothing architecturally.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- PRACTICE: Harden the session cookie: HttpOnly + Secure + SameSite=Lax (or Strict), narrow Path, no session ID in URLs, and regenerate the session ID on login and on privilege change
  WHY: HttpOnly blocks XSS token theft (never put the session token in localStorage), Secure prevents cleartext leakage, SameSite gives baseline CSRF resistance, and ID regeneration on authentication defeats session fixation. ASVS 5.0 V7 requires session tokens be invalidated/rotated at these boundaries and that all timeout logic be enforced server-side, never in the client.
  SOURCE: https://asvs.dev/v5.0.0/V7-Session-Management/
- PRACTICE: Follow NIST SP 800-63B Rev. 4 (final, Aug 2025) for passwords: minimum 8 chars with MFA / 15 chars if password-only, allow up to 64+, NO composition rules, NO periodic expiration, blocklist check against known-breached/common passwords, allow paste and password managers
  WHY: Rev. 4 is the current authoritative baseline and explicitly says verifiers SHALL NOT impose composition rules and SHALL NOT require periodic changes (change only on evidence of compromise). Length + blocklist beats complexity theater. This is the citation to hand to any agency reviewer who asks for 'uppercase+symbol+90-day expiry'.
  SOURCE: https://pages.nist.gov/800-63-4/sp800-63b.html
- PRACTICE: Throttle failed logins instead of hard-locking accounts: rate-limit per-account (NIST caps at no more than 100 consecutive failures) with progressive delays, backed by Redis counters
  WHY: NIST 800-63B requires rate limiting but discourages aggressive hard lockout, because hard lockout lets anyone who knows a username (trivially guessable in a government office: firstname.lastname) deny service to that employee. Progressive throttling (e.g., exponential backoff after 5 failures) achieves the security goal without the DoS vector; every throttle event still lands in the audit log.
  SOURCE: https://pages.nist.gov/800-63-4/sp800-63b.html
- PRACTICE: Hash passwords with Argon2id (argon2-cffi via pwdlib), per OWASP Password Storage guidance
  WHY: Argon2id is OWASP's first-choice password hash (memory-hard, GPU-resistant). passlib is effectively unmaintained; pwdlib is the maintained FastAPI-ecosystem successor. Parameters (memory/iterations/parallelism) should be recorded in tech-stack.md per standing rule 9.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- PRACTICE: Session lifetimes: absolute timeout of 12 hours (one workday) and idle timeout of 30â€“60 minutes, both enforced server-side, with the chosen values documented as a risk decision
  WHY: NIST 800-63B-4 at AAL2 sets an overall reauthentication timeout that SHOULD be â‰¤24h and idle timeout SHOULD be â‰¤1h; ASVS 5.0 requires the inactivity timeout to match documented risk analysis. A 12h absolute / 30-min idle for approver+admin roles and 60-min idle for ordinary staff fits an 8-hour government office day and keeps unattended shared-office PCs from staying logged in.
  SOURCE: https://pages.nist.gov/800-63-4/sp800-63b.html
- PRACTICE: Model RBAC in tables, not code enums: core_roles, core_permissions, core_role_permissions, core_user_roles; authorize against permission strings (e.g., 'reimb.claim.approve'), never role names
  WHY: Multi-tenant + configurable is the whole product thesis: a second tenant WILL want different role compositions, and table-driven roleâ†’permission mapping makes that an admin-console operation instead of a deploy. Code checks permissions ('can this principal approve claims?'), the DB decides which roles carry it. Permissions themselves are seeded by Alembic data migrations and referenced from code constants, with a startup/test check that every constant exists in the DB â€” the classic RBAC (roleâ†’permission indirection) model per NIST's RBAC work.
  SOURCE: https://csrc.nist.gov/projects/role-based-access-control
- PRACTICE: Scope approval roles by org unit: a core_org_units self-referencing hierarchy, and an org_unit_id column on core_user_roles so a grant reads 'Division Chief OF the BLHSD Finance Section'
  WHY: In a government office, who may approve is inseparable from where: a division chief approves claims of their division only. Putting the scope on the role assignment (nullable org_unit_id = global grant) keeps one mechanism for both global roles (admin) and scoped roles (approver), and lets the reimbursement workflow resolve the approver by walking the requester's org-unit ancestry.
- PRACTICE: Admin-managed provisioning only â€” no self-registration; accounts are created/deactivated by admins from the staff directory, and 'offboarding' is deactivation, never deletion
  WHY: Staff population is a closed, HR-known set; self-registration adds an unauthenticated attack surface and an identity-proofing problem for zero benefit. Deactivation (is_active=false + session revocation) instead of deletion preserves FK integrity and the hash-chained audit trail â€” which also happens to be exactly what the project's soft-delete rule already mandates. Every provisioning event (create, role grant/revoke, deactivate, password reset) is itself an audited action with an acting admin.
- PRACTICE: Make Active Directory/LDAP an optional, feature-flagged authentication backend: bind-as-user over LDAPS/StartTLS (never plain 389, never anonymous bind), escape all filter input, run ldap3 calls off the event loop, and keep the local DB as the sole source of truth for roles
  WHY: On a Windows Server government network, AD SSO-ish login ('use your domain password') is a likely eventual ask, but it must not be a launch dependency. The safe shape: AD only answers 'is this password correct for this staff member' (authentication); Office-Connect's own tables answer everything else (authorization), with optional AD-groupâ†’role mapping as a convenience import. TLS-by-default and no-anonymous-bind are the baseline; blocking LDAP I/O inside async FastAPI handlers will stall the event loop, so wrap it (run_in_executor) or use an async-first wrapper.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/LDAP_Injection_Prevention_Cheat_Sheet.html
- PRACTICE: Audit the full authentication lifecycle into the hash-chained core_audit_logs: login success, login failure (with attempted username, source IP, user agent), throttle/lockout trigger, logout, session expiry/revocation, password change/reset, and every role grant/revoke
  WHY: ASVS V7/V16 and general government-audit expectations require security-relevant events to be attributable and tamper-evident; the hash chain already built in Phase 0 gives tamper evidence for free. Log the event, never the credential â€” no passwords, no session tokens in logs. Failed-login records enable the throttling counters AND the 'who tried to get into the Director's account' question later.
  SOURCE: https://asvs.dev/v5.0.0/V7-Session-Management/
- PRACTICE: Because auth is cookie-based, add explicit CSRF defense for all state-changing endpoints: SameSite=Lax as the floor plus a custom-header or double-submit token check for the React frontend
  WHY: The one real cost of choosing cookies over Authorization-header JWTs is CSRF. SameSite alone is not sufficient defense-in-depth per OWASP; since the React app is same-origin and always uses fetch/XHR, requiring a custom header (which cross-site form posts cannot set) is cheap and robust.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
- PRACTICE: Concurrent-session policy: permit a small bounded number of sessions per user (e.g., 3), expose 'active sessions' with remote-revoke in the admin console and the user's own profile, and consider single-session for admin-role accounts
  WHY: Hard single-session policies frustrate legitimate desk+laptop use and give attackers a signal (logging in kicks the real user out, alerting them but also enabling harassment). Redis makes per-user session indexing trivial (a set of session IDs keyed by user), which is also the mechanism for 'revoke all sessions on password change/deactivation' â€” an ASVS requirement.
  SOURCE: https://asvs.dev/v5.0.0/V7-Session-Management/

## PITFALLS
- Choosing JWTs 'because FastAPI tutorials use OAuth2PasswordBearer' and ending up with tokens that cannot be revoked when an employee is terminated â€” or 'fixing' it with a Redis denylist, at which point you have rebuilt server-side sessions with extra steps and a signing key to protect.
- Storing any auth token in localStorage/sessionStorage â€” readable by any XSS payload; the session identifier must live only in an HttpOnly cookie.
- Copying legacy password policy (uppercase+digit+symbol, 90-day forced expiry) into the new system. NIST 800-63B Rev. 4 explicitly prohibits both for verifiers; if a Philippine agency ICT policy still mandates them, record it as a documented deviation in the module doc rather than silently adopting it as 'best practice'.
- Hard account lockout after N failures: with guessable government usernames, anyone can lock out the whole Finance section before payroll cutoff. Throttle with backoff instead, and audit the throttle events.
- Session fixation: reusing the pre-login session ID after authentication. Always issue a fresh session ID at login and destroy the server-side record at logout (deleting the cookie alone is not logout).
- Enforcing idle timeout in the React app only (JS timer that 'logs you out') while the server-side session stays valid â€” ASVS requires server-side enforcement; the client timer is UX, not security.
- Hardcoding role checks ('if role == "admin"') across modules instead of permission checks â€” every new tenant or org restructure then requires code changes, defeating the configurable-multi-tenant premise, and it invites cross-module coupling the lint-imports rule exists to prevent.
- Letting AD group membership directly drive authorization at request time: an AD outage then breaks permission checks, AD admins outside the app silently change who can approve money, and the app's audit chain has no record of the change. AD authenticates; Office-Connect's tables authorize.
- LDAP mistakes on Windows networks: plain-text bind on port 389, anonymous bind fallbacks (some AD configs treat empty-password bind as anonymous success â€” an authentication bypass), unescaped user input in LDAP filters (LDAP injection), and synchronous ldap3 calls blocking the async event loop.
- No break-glass path: if AD login is the only method and the domain controller or the feature-flag config store is down, nobody can administer the app. Keep at least one local, MFA-protected admin account that bypasses the LDAP backend.
- User enumeration through asymmetric responses: 'wrong password' vs 'no such user', different HTTP timing, or lockout messages that confirm an account exists. Return one generic failure message; keep the distinction only in the audit log.
- Hard-deleting users or their role assignments â€” breaks audit-chain attribution and violates the project's own soft-delete rule; revoked grants should be soft-deleted rows so 'who could approve claims in March' remains answerable.
- Forgetting CSRF protection after choosing cookie sessions, or setting SameSite=None; also forgetting to revoke all existing sessions on password change and on account deactivation.
- Building the login flow before deciding the multi-tenancy boundary: the session must carry tenant context and every permission check must be tenant-scoped, or a second tenant's admin can grant roles in the first tenant.
- Logging secrets: passwords (even failed attempts' passwords), session IDs, or password hashes must never appear in core_audit_logs or app logs â€” log the event metadata only.

## RECOMMENDATIONS
- Adopt cookie + Redis server-side sessions as the auth architecture: opaque 128-bit+ random session ID (secrets.token_urlsafe) in an HttpOnly, Secure, SameSite=Lax cookie; session record in Redis keyed 'session:{id}' holding user_id, tenant_id, role/permission snapshot version, created_at, last_seen_at, ip, user_agent; plus a per-user Redis set 'user_sessions:{user_id}' to enable revoke-all and the concurrent-session cap. Document the decision (and the JWT rejection rationale) in docs/standards/ or the module doc.
- Schema (follows the DB quick card): core_users, core_roles (lookup, is_active), core_permissions (lookup, seeded via Alembic data migration, string codes like 'reimb.claim.approve'), core_role_permissions, core_user_roles (user_id, role_id, nullable org_unit_id for scoped grants, full ownership + soft-delete columns), core_org_units (self-referencing parent_org_unit_id), and an append-only core_login_attempts (created_* only, documented exception like the audit log). All auth mutations also emit hash-chained core_audit_logs entries.
- Authorization API: a single FastAPI dependency require_permission('reimb.claim.approve', scope=OrgUnitScope.REQUESTER) that resolves the user's effective permission set (cached in Redis, invalidated by bumping a per-user permissions-version on any grant/revoke). Modules import this from core only â€” never role-name checks in module code, preserving the no-cross-module-imports rule.
- Password policy (cite NIST SP 800-63B-4 in the standards doc): minimum 12 characters as house policy (Rev. 4 floor is 8 with MFA / 15 password-only), max 64+, Unicode allowed, no composition rules, no scheduled expiry, blocklist check on set/change (bundle a top-100k list on-prem â€” no cloud calls, consistent with the no-cloud constraint), allow paste. Hash with Argon2id via pwdlib/argon2-cffi and record parameters in tech-stack.md (rule 9). Plan TOTP MFA for admin and approver roles as a fast-follow; it materially changes the risk profile of money-approving accounts.
- Login throttling in Redis: per-account and per-IP counters; after 5 consecutive failures apply exponential backoff delays (never a permanent lock an attacker can weaponize), ceiling well under NIST's 100-consecutive-failure cap; counter resets on success; every failure and every throttle event written to core_login_attempts and the audit chain with IP + user agent. Generic error message regardless of failure cause.
- Session lifetimes (write into ui/workflow standards as a documented risk decision per ASVS): absolute 12h, idle 60 min for staff, idle 30 min for users holding approver/admin roles; enforced by checking created_at/last_seen_at server-side on every request; sliding refresh of last_seen_at; re-authentication required for high-impact actions (changing own password, granting roles).
- Provisioning: admin-console-only user lifecycle (create from staff directory, assign scoped roles, reset password with forced change on first login, deactivate). No self-registration endpoint at all â€” do not build it behind a flag. Deactivation sets is_active=false AND deletes all Redis sessions immediately. Password reset and deactivation revoke all sessions; role changes bump the permission-cache version so they take effect on the next request, not the next login.
- AD/LDAP integration: design the auth service with a pluggable verifier interface now (LocalPasswordVerifier first), implement LdapVerifier later behind a feature flag that fail-safes OFF per the standing rule. When implemented: LDAPS or StartTLS only, reject empty passwords before bind (anonymous-bind bypass), escape DN/filter input with ldap3's escape utilities, run binds in a threadpool, look up the user via a least-privilege service account then bind as the user, and map AD groups to core_roles only as an explicit admin-approved import â€” never live at request time. Keep at least one local break-glass admin account excluded from the LDAP path.
- CSRF: since auth is cookie-based, require a custom header (e.g., X-Requested-With or a double-submit token) on every non-GET API route via middleware, on top of SameSite=Lax. Add this to the API conventions doc so the future React frontend bakes it into its fetch wrapper from day one.
- Audit events to emit from day one (they ride the existing hash chain): auth.login.success, auth.login.failure, auth.login.throttled, auth.logout, auth.session.revoked (with actor â€” self vs admin), auth.password.changed, auth.password.reset, rbac.role.granted, rbac.role.revoked, user.created, user.deactivated. Include actor_user_id, target_user_id, tenant_id, ip, user_agent; never the credential. This satisfies the ASVS session/audit expectations and makes the admin console's 'security log' view a pure read of existing data.
- Sequence it as the shared-auth increment of Phase 0/1, before Local Travel Reimbursement, since claim approval depends on org-unit-scoped roles: (1) users+roles+permissions schema and Alembic seeds, (2) session service on Redis + login/logout endpoints + throttling, (3) require_permission dependency + org-unit scoping, (4) admin provisioning endpoints, (5) audit wiring â€” each landing with its delta register entry and tech-stack.md updates per the session contract.
