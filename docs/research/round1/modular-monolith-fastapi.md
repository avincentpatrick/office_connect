# agent4
TOPIC: Modular monolith structure for Python/FastAPI with async SQLAlchemy, plus lightweight config-driven multi-tenancy â€” tailored to Office-Connect

## KEY PRACTICES
- PRACTICE: Package-by-module, not package-by-layer: each domain module is a self-contained package with its own router.py, schemas.py, models.py, service.py, dependencies.py, exceptions.py, constants.py
  WHY: File-type layouts (all routers together, all models together) stop scaling once a monolith has several domains; per-module packages keep a feature's whole vertical slice in one place, make ownership obvious, and are the unit that import-linter contracts can police. This is the dominant convention in the FastAPI community for larger apps.
  SOURCE: https://github.com/zhanymkanov/fastapi-best-practices
- PRACTICE: Enforce boundaries mechanically with import-linter contracts: 'forbidden' (core never imports modules), 'independence' (modules never import each other), and 'layers' (api â†’ service â†’ models inside each module, applied to all modules via containers)
  WHY: Boundaries that exist only in documentation erode; import-linter turns them into CI failures. The five built-in contract types (forbidden, protected, layers, independence, acyclic siblings) cover the whole modular-monolith rule set, and wildcards (office_connect.modules.*) let one layers contract govern every current and future module automatically.
  SOURCE: https://import-linter.readthedocs.io/en/stable/contract_types/index.html
- PRACTICE: Give every module an explicit public surface (e.g. modules/<name>/public.py or interface registration) and treat everything else as private implementation; cross-module consumers may only touch the public surface
  WHY: Without a declared public API, 'independence' either blocks all reuse or gets riddled with ignore_imports exceptions. A small public facade per module gives you microservice-grade encapsulation while keeping in-process call speed, and makes a later extraction a mostly mechanical exercise.
  SOURCE: https://github.com/Khaled-Farhat/modular-monolith-practice
- PRACTICE: Cross-module communication via (a) service interfaces defined as Protocols in the shared core with implementations registered at the composition root (main.py), and (b) an in-process event bus for fire-and-forget side effects; never import another module's models or services directly
  WHY: Dependency inversion through core-hosted interfaces keeps the independence contract green while still allowing synchronous queries (e.g., DMWIS asking the directory module for a staff record). In-memory application events decouple side effects (notify, log, sync) and are the recognized stepping stone to an outbox/broker if reliability demands grow. The key discipline: modules depend on contracts, not on each other.
  SOURCE: https://binaryigor.com/modular-monolith-dependencies-and-communication.html
- PRACTICE: Shared core owns cross-cutting infrastructure only (DB session, declarative Base, audit chain, soft-delete filtering, time handling, feature flags, tenant config, auth/RBAC, staff directory); modules own their business tables and logic; core must never grow business logic
  WHY: A thin, stable core is what lets modules stay independent â€” if business rules leak into core, every module transitively couples to every other module's rules and the 'core never imports modules' contract stops meaning anything. Shared auth/RBAC and the staff directory belong in core because every module consumes them identically.
- PRACTICE: One SQLAlchemy MetaData/Base for the whole app, with cross-module references expressed as plain FK columns (<singular>_id) resolved through service interfaces â€” not ORM relationship() objects that span module boundaries
  WHY: A single metadata keeps Alembic autogenerate and FK integrity simple (right for a single-DB monolith), but ORM relationships across modules create import cycles and hidden joins that defeat the boundary. An FK column plus an interface call preserves referential integrity at the DB level without code-level coupling.
- PRACTICE: Alembic across modules: start with a single linear revision history; if modules later need independent migration streams, use version_locations for per-module directories, branch_labels for named streams, depends_on for cross-module ordering, and 'alembic upgrade heads' â€” plus a CI guard that fails on unexpected multiple heads
  WHY: Alembic's branch machinery (labeled bases per module directory, topologically sorted depends_on) is explicitly designed for module-per-directory monoliths, but it adds real cognitive cost; a solo/small team on one DB is better served by one linear chain with module-prefixed revision messages until parallel contributors force the split. Multiple accidental heads are the classic failure mode either way.
  SOURCE: https://alembic.sqlalchemy.org/en/latest/branches.html
- PRACTICE: Gate whole modules with feature flags at a single choke point â€” a router-level dependency such as require_module('reimbursement') that 404s when the flag is off â€” rather than sprinkling flag checks through services; keep flag decision points few, at the edges, and default OFF
  WHY: Feature-toggle literature is emphatic that toggle points must be minimized and centralized or they metastasize into permanent conditional complexity; one dependency on the module's APIRouter gates every endpoint at once, works with DB/Redis-driven flags (unlike conditional router mounting, which is fixed at startup), and fail-safe OFF means a flag-store outage disables features instead of exposing them.
  SOURCE: https://martinfowler.com/articles/feature-toggles.html
- PRACTICE: Testing strategy per module: (1) unit tests of services with faked interfaces/events, (2) per-module API tests against an app factory that mounts core + only the module under test, (3) contract tests for every core-hosted Protocol interface, (4) a thin cross-module integration suite for event flows and migrations
  WHY: Booting only core+one-module per test suite is itself a boundary test â€” it fails the moment a hidden cross-module import sneaks in â€” and keeps suites fast. Contract tests pin the inter-module agreements so a provider module can change internals freely, which is the whole payoff of the architecture.
- PRACTICE: Lightweight single-DB configurability: model per-tenant behavior as a validated settings table (namespaced key â†’ typed value with a Pydantic schema registry per key) plus feature flags, and defer tenant_id row-level tenancy until two offices actually share one database
  WHY: The shared-database/shared-schema + tenant_id pattern with automatic query filtering is the standard heavyweight answer, but it taxes every query and every test; for single-instance-per-office deployment, 'multi-tenant' really means 'config-driven behavior', which a settings table + flags delivers with zero query overhead. If row tenancy is ever needed, SQLAlchemy's with_loader_criteria (the same mechanism as a soft-delete filter) is the analog of EF Core's global query filter.
  SOURCE: https://learn.microsoft.com/en-us/ef/core/miscellaneous/multitenancy
- PRACTICE: Treat splitting into services as a last resort triggered by concrete signals (independent deploy cadence, team scaling, isolated load hotspots), and prepare for it only via the patterns you already need â€” public interfaces, events, no shared models â€” not by pre-building distribution
  WHY: The clearest migration paths out of a monolith (outbox, background data sync, interface-based clients) are exactly the disciplines that make a monolith healthy anyway, so the option to split stays open at near-zero cost; actually splitting on an on-prem single Windows Server adds network failure modes, distributed transactions, and ops burden with no upside. Offload load hotspots (report generation, document processing) to Celery workers instead â€” that is the split that architecture already gives for free.
  SOURCE: https://binaryigor.com/modular-monolith-dependencies-and-communication.html

## PITFALLS
- The independence contract in pyproject.toml lists modules manually ('append each new module here') â€” a forgotten append silently exempts a new module from boundary checking. A tiny CI script should assert that every directory under office_connect/modules/ appears in the contract list.
- Sharing SQLAlchemy models or Pydantic schemas across modules 'just this once' â€” the most common way modular monoliths rot. Cross-module relationship() objects create import cycles that import-linter will catch late and painfully; cross-module schema reuse couples API contracts so one module's field rename breaks another's endpoint.
- Publishing in-process events synchronously inside the DB transaction without deciding failure semantics: if a subscriber raises, does the commit roll back? Pick a rule (dispatch after commit for side effects; in-transaction only for invariants) and encode it in the bus, or you get heisenbugs the first time a notification handler fails.
- Alembic multiple-heads surprises: two sessions each add a migration from the same parent and 'alembic upgrade head' starts erroring in CI or, worse, on the production Windows Server. Guard with a CI step that counts heads, and merge or reorder immediately.
- Feature flag OFF but the module's routers, event subscribers, and Celery tasks still run â€” gating only HTTP endpoints while background jobs keep executing is a classic partial-gate bug. The require_module gate must have counterparts in Celery task entry points and event subscribers.
- Reading feature flags or tenant config from PostgreSQL on every request â€” cache in Redis or in-process with a short TTL, but ensure the cache failure mode is still fail-safe OFF for flags (and never lets /api/v1/config 500).
- The tenant-config table degenerating into an untyped key-value junk drawer where a typo'd key silently returns the default. Every config key needs a registered Pydantic type/validator and unknown keys should fail loudly at write time.
- core becoming a god module: 'it's shared by two modules, put it in core' turns core into a dumping ground that every module couples to. Core takes infrastructure and genuinely universal domain concepts (users, roles, staff directory) only; duplication between two modules is usually cheaper than a wrong shared abstraction.
- Alembic env.py must import every module's models for autogenerate to see them â€” but env.py living inside the linted package would violate 'core never imports modules'. Keep env.py (and main.py's composition root) outside the contract scope or explicitly ignored, and make model registration explicit so a forgotten import doesn't cause autogenerate to emit DROP TABLE for a module's tables.
- Testing only through the fully-assembled app: slow suites, and hidden cross-module coupling never surfaces because everything is always imported. Conversely, module-only test apps that fake too much can pass while the composed app fails startup â€” keep at least one smoke test that boots the full app with all flags on and off.
- Blindly following external conventions that conflict with locked local standards â€” e.g., fastapi-best-practices recommends singular table names, but Office-Connect's binding standard is prefixed plural; standards docs take precedence and deltas get recorded per the module-doc rule.
- Premature extraction to microservices (or 'preparing' by adding HTTP calls between modules in-process) â€” you pay the distributed-systems tax on a single on-prem server that cannot even scale horizontally, and lose the transactional simplicity that makes the audit chain and soft-delete rules easy to enforce.

Add the CI check that every modules/ subdirectory is listed in the independence contract.
- Create core/interfaces.py holding Protocol classes for anything one module will need from another (e.g., StaffDirectory, DocumentStore later), plus a small registry; main.py wires implementations at startup. Modules import only office_connect.core, so all existing contracts stay green while cross-module calls remain possible.
- Add core/events.py: a minimal in-process event bus (dataclass events, subscribe(event_type, handler), dispatch after session commit via SQLAlchemy after_commit or an explicit unit-of-work hook). Use it for cross-module side effects (e.g., reimbursement approved â†’ notification/activity feed). If durable delivery is ever needed, upgrade the dispatch to write an outbox row consumed by a Celery beat task â€” the subscriber code does not change.
- Implement module gating as a single dependency: require_module("reimbursement") attached to the module's top-level APIRouter via dependencies=[...], returning 404 when core_feature_flags says off (fail-safe OFF on any flag-store error, consistent with the existing rule that /api/v1/config never 500s). - Keep the single alembic/versions/ directory and linear history for now (one developer, one DB). Adopt the discipline of prefixing revision messages with the module ("reimb: create reimb_claims"), and add a QA-gate script asserting exactly one head (python -m alembic heads | expect 1 line). Only introduce version_locations + branch_labels + depends_on if a second contributor or an independently-versioned module makes parallel migration streams real â€” document that trigger in database-standards.md.
- In alembic/env.py, import models via one explicit registry function (e.g., office_connect.core.models plus each module's models module listed in one place next to the router-mounting list in main.py) and enable compare_type/compare_server_default; since env.py and main.py sit at the composition root, exempt them (not the modules) from import-linter if the tool flags them.
- Structure tests as tests/core/, tests/modules/reimbursement/, tests/integration/: give conftest.py an app_factory(modules=[...]) fixture so each module's API tests boot core + that module only â€” this doubles as a runtime boundary check. Add contract tests for every Protocol in core/interfaces.py, an integration smoke test booting the full app with all flags off (everything must 404 cleanly, config endpoint must still answer), and keep lint-imports in every phase QA gate as already mandated.
- For cross-module data at the DB level, allow plain FK columns to another module's table (e.g., reimb_claims.user_id â†’ core_users.id is core, fine; a future dmwis_documents.claim_id â†’ reimb_claims.id) but forbid ORM relationship() across module boundaries in the standards doc; the consuming module fetches the related object through the owning module's public interface.
- Multi-tenancy: keep the existing core_tenant_configs as the configurability spine, but harden it â€” namespaced keys (reimb.rate_per_km, core.office_name), a Pydantic model registered per namespace so values are validated on write and typed on read, is_active + audit columns per your lookup standard, and Redis-cached reads surfaced through /api/v1/config. Per-module settings defaults live in each module's config.py (decoupled BaseSettings per domain, per fastapi-best-practices) with the tenant table overriding them. Do NOT add tenant_id columns now; record in database-standards.md that if two offices ever share one DB, the upgrade path is tenant_id + a with_loader_criteria global filter exactly like the existing soft-delete filter.
- Since deployment is one on-prem Windows Server, resolve load concerns inside the monolith: route heavy work (report generation, CSS-IS survey exports, document processing) to Celery queues with per-module queue names (reimb, dmwis, css) so a flooded queue never starves another module â€” that is the operational isolation microservices would have bought, at none of the cost.
- Write the 'when to split' policy down once in docs/standards/tech-stack.md so the question stops recurring: split a module out only when (a) it needs a different deploy cadence than the rest, (b) a distinct team owns it, or (c) it needs isolation the Celery-queue approach cannot give; until then the public.py + events + no-shared-models discipline keeps extraction cheap.
