# agent5
TOPIC: Government internal-app UI best practices for Office-Connect: GOV.UK/USWDS patterns (task lists, one-thing-per-page, status tags, error summaries, check-answers/confirmation, save-and-return), WCAG 2.2 AA for forms-heavy apps, approval-queue table patterns, printable/PDF form outputs, and Philippine government web mandates

## KEY PRACTICES
- PRACTICE: Use the GOV.UK task list pattern ('Complete multiple tasks') for transactions with multiple sections completed over several sessions: verb-named tasks, flexible completion order where possible, status per task ('Completed' as plain black text, 'Incomplete/Not yet started' blue tag, 'Cannot start yet' grey text with the row unlinked, 'There is a problem' red tag reserved for errors), aria-describedby linking task name to status.
  WHY: It breaks a long government transaction (like a reimbursement claim) into resumable chunks, shows progress at a glance, and encodes prerequisite ordering without hiding tasks; it is the most battle-tested cross-government pattern for exactly this shape of work.
  SOURCE: https://design-system.service.gov.uk/patterns/complete-multiple-tasks/
- PRACTICE: Start form design with one thing per page (one question/decision per screen), then merge pages only where research shows users handle more; GOV.UK explicitly notes that for forms used regularly by the same users (i.e., internal staff tools) more things per page can make sense.
  WHY: One-thing-per-page handles errors, branching, and save-points cleanly and helps low-confidence users, but expert daily users (approvers, admins) are slowed by excessive page churn â€” the guidance itself sanctions denser pages for repeat internal users.
  SOURCE: https://www.gov.uk/service-manual/design/form-structure
- PRACTICE: On any validation failure, render a GOV.UK-style error summary at the top of the main content: heading 'There is a problem', role=alert, keyboard focus moved to it, each error an anchor link to the offending field (first field of a group for radios/dates), 'Error: ' prefixed to the page <title>, and summary text identical to the inline error message beside each field.
  WHY: Screen-reader and keyboard users discover all errors immediately instead of hunting; matched summary/inline wording prevents disorientation; this single component resolves most WCAG 3.3.x form-error obligations.
  SOURCE: https://design-system.service.gov.uk/components/error-summary/
- PRACTICE: Status tags: sentence case (never uppercase), adjective wording, light background with dark text, one consistent color per status everywhere in the product, and never color alone â€” the text label always carries the meaning. Keep the status vocabulary minimal; sometimes 'Completed' vs unmarked is enough.
  WHY: GOV.UK deprecated uppercase solid tags because they read poorly and look clickable; color-only status fails WCAG 1.4.1; inconsistent status colors across modules destroys learnability in a multi-module platform.
  SOURCE: https://design-system.service.gov.uk/components/tag/
- PRACTICE: End every submission flow with a 'Check your answers' page (editable rows linking back to the source question, answers reworded as statements, submit button naming the real action e.g. 'Submit claim') followed by a confirmation page carrying: reference number, what happens next and when, contact details, and a way to save a record of the transaction.
  WHY: Check-answers catches errors before they enter the approval chain (cheaper than rejection round-trips), and the confirmation page is what stops 'did it go through?' phone calls and duplicate submissions in a government office.
  SOURCE: https://design-system.service.gov.uk/patterns/confirmation-pages/
- PRACTICE: USWDS 'Complete a complex form' guidance: show progress with a step indicator, let users complete sections in their chosen order where possible, warn and confirm before an answer change invalidates already-completed dependent steps, and support save-and-resume â€” telling users up front that progress is saved.
  WHY: Multi-step government forms are abandoned or corrupted when users cannot see where they are, lose work, or silently invalidate earlier answers; explicit up-front save messaging reduces anxiety-driven rushed completion.
  SOURCE: https://designsystem.digital.gov/patterns/complete-a-complex-form/progress-easily/
- PRACTICE: Save-and-return: place a 'Save and come back later' affordance on every page of a multi-page flow (GOV.UK positions it directly under the primary action), persist drafts server-side keyed to the authenticated user, and give a clear resume entry point ('continue a saved claim') on return.
  WHY: Reimbursement claims need receipts, itineraries and certificates the claimant rarely has in one sitting; without first-class draft persistence, users resort to keeping data in Word files or abandoning mid-flow.
  SOURCE: https://sign-in.service.gov.uk/documentation/design-recommendations/save-progress
- PRACTICE: WCAG 2.2 AA form essentials: 3.3.7 Redundant Entry (A) â€” never make users re-type information the system already has in the same process (auto-populate or offer to select); 3.3.8 Accessible Authentication (AA) â€” no cognitive puzzles/CAPTCHA-only logins; 2.5.8 Target Size (AA) â€” interactive targets at least 24x24 CSS px or spaced; 2.4.11 Focus Not Obscured (AA) â€” sticky headers/footers must not fully hide the focused element; 2.5.7 Dragging Movements (AA) â€” every drag interaction needs a click alternative; 3.2.6 Consistent Help (A) â€” help/contact mechanism in the same relative place on every page. Note 4.1.1 Parsing was removed in 2.2.
  WHY: These are the criteria a forms-heavy internal app most commonly fails, they are cheap to satisfy at design time and expensive to retrofit, and 2.2 AA is the current international benchmark government buyers audit against.
  SOURCE: https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/
- PRACTICE: Approver/caseworker queues: use the MOJ Design System 'filter a list' pattern (a filter panel with removable applied-filter chips) combined with the sortable table component (ascending/descending on the columns that matter), plus pagination and a visible result count.
  WHY: MOJ built and researched these specifically for casework lists â€” the closest published government analogue to an approval queue â€” and combining filter + sort + count is what keeps a queue usable once it passes a few dozen rows.
  SOURCE: https://design-patterns.service.justice.gov.uk/patterns/filter-a-list
- PRACTICE: For staff-facing (internal) services, follow the UK pattern of a dedicated internal design layer that extends the citizen-facing system rather than reusing it verbatim: the Home Office Design System publishes internal/caseworker patterns (logging in, writing reports, case screens) layered on GOV.UK components.
  WHY: Internal users are trained, frequent, and task-dense; a thin internal layer over the same tokens/components preserves consistency while allowing denser, keyboard-friendly screens than citizen-facing rules would permit.
  SOURCE: https://design.homeoffice.gov.uk/design-system/patterns
- PRACTICE: USWDS 'Keep a record' pattern for printable/PDF outputs: give a printable or downloadable record of every submission with a title block (office name, date, confirmation of submission), reference number, next steps, and full question/answer recap; provide a real PDF (print-to-PDF is 'not widely understood' and poor on mobile); print styles use white background, dark 12pt+ serif text, minimal graphics, no tables/headings split across pages, and masked sensitive values (last 4 digits).
  WHY: Philippine government offices still run on signed paper attachments to vouchers; a properly structured generated PDF is the bridge between the digital workflow and the physical DV/liquidation file, and print-optimized output is an accessibility feature, not a nicety.
  SOURCE: https://designsystem.digital.gov/patterns/complete-a-complex-form/keep-a-record/
- PRACTICE: Generate official PDFs server-side from HTML/CSS templates (Chromium-based or HTML-to-PDF library) as part of the backend workflow, not in the browser; treat the generated document as an archival artifact with consistent fonts, layout and page headers.
  WHY: Browser-side generation produces inconsistent layout across machines and cannot be trusted as the authoritative copy of a government form; server-side generation gives one canonical, storable, auditable rendering.
  SOURCE: https://www.smashingmagazine.com/2019/06/create-pdf-web-application/
- PRACTICE: Philippine mandate â€” web accessibility: DICT Memorandum Circular 004-2017 prescribes W3C WCAG (via ISO/IEC 40500:2012) as the Philippine national standard for government web content, binding on all national government departments, bureaus and offices including DOH.
  WHY: This makes accessibility a compliance requirement for Office-Connect, not a preference; the MC references WCAG 2.0, so building to WCAG 2.2 AA satisfies the national policy with headroom.
  SOURCE: https://dict.gov.ph/wp-content/uploads/2017/10/DICT-MC-004-2017-PRESCRIBING-THE-PHILIPPINES-WEB-ACCESSIBILITY-POLICY-AND-ADOPTING-FOR-THIS-PURPOSE-ISO-IEC-405002012-INFORMATION-TECHNOLOGY-W3C-WEB-CONTENT-ACCESSIBILITY-GUIDELINES-WCAG-2.0-A.pdf
- PRACTICE: Philippine mandate â€” E-Governance Act (Republic Act No. 12254, signed September 2025; IRR signed March 2026): institutionalizes digital government across agencies, explicitly covering internal systems as well as public-facing ones, and mandates cybersecurity and interoperability standards under DICT.
  WHY: Office-Connect is exactly the class of internal government system this law now governs; aligning early (audit trails, secure data sharing, DICT interoperability expectations) future-proofs a DOH bureau deployment.
  SOURCE: https://mb.com.ph/2026/03/24/e-governance-act-irr-signed-mandates-cybersecurity-interoperability-across-agencies
- PRACTICE: Philippine web identity: the Government Website Template Design (GWTD) guidelines and the newer DICT NGA Web Template standardize the look, navigation and required content of Philippine government websites (official masthead, transparency seal, agency identity).
  WHY: These apply to public-facing government web presence; Office-Connect's internal screens are out of scope, but any public-facing surface (landing page, published survey links from CSS-IS) should follow the template conventions to read as legitimate government property.
  SOURCE: https://i.gov.ph/policies/signed/memorandum-circular-rules-regulations-migrating-gwhs-dost-ict-office/annex-c-government-website-template-design-gwtd-guidelines/
- PRACTICE: Approval/case detail screens keep decision context in view: full-page detail views (not modals) with a persistent summary panel (claimant, amount, status, reference) that stays visible while the approver scrolls receipts and history, and a visible activity timeline of who did what when.
  WHY: Approvers make faster, safer decisions when the money amount, claimant identity, and history never scroll out of view; modal-based review loses queue position and hides context, and it risks WCAG 2.4.11 focus-obscured failures.

## PITFALLS
- Uppercase, solid-color, or color-only status tags â€” GOV.UK deprecated uppercase tags as hard to read and button-like, and color-only status fails WCAG 1.4.1; every status needs a text label and one consistent color per status across all modules.
- Applying one-thing-per-page dogmatically to expert internal users: approvers processing dozens of claims a day will hate 12-click reviews â€” GOV.UK itself says regularly-used internal forms can carry more per page; reserve strict one-thing-per-page for infrequent claimant-facing flows.
- Relying on browser print-to-PDF as the official record â€” USWDS notes users don't understand it and it barely works on mobile; the authoritative copy must be a server-generated PDF stored with the claim.
- Making staff re-enter data the system already knows (name, position, division, salary grade, station) â€” this now fails WCAG 2.2 3.3.7 Redundant Entry at Level A, and it is the single biggest annoyance in government form apps.
- Losing draft state on validation error, session timeout, or browser back â€” multi-step flows must persist per-step server-side; a claimant who loses 20 minutes of itinerary entry will revert to paper.
- Rendering 'Cannot start yet' tasks as clickable links, or hiding them entirely â€” the GOV.UK pattern shows them as visible grey unlinked rows so users understand the full journey and its prerequisites.
- Error summary and inline field errors with different wording, or a summary that doesn't receive focus â€” both break the screen-reader contract the pattern exists to provide.
- Sticky headers, sticky action bars, or toast overlays that cover the keyboard-focused element â€” a new, commonly-failed WCAG 2.2 AA criterion (2.4.11 Focus Not Obscured) in dashboard-style internal apps.
- Approval queues with no pagination, no result count, no empty state, and unlabeled icon-only action buttons â€” queues degrade fast past ~50 rows without filter chips, sortable columns and counts.
- Modal dialogs for claim review/approval decisions â€” loses queue position, hides context, traps focus badly; use full-page detail views with a back-to-queue link that restores filters.
- Assuming the Philippines has a full internal-app design system to comply with â€” GWTD/NGA templates govern public website identity only, and DICT MC 004-2017 cites WCAG 2.0; the correct move is GOV.UK/USWDS patterns + WCAG 2.2 AA, with PH mandates recorded as compliance floor, not design source.
- Inventing many bespoke workflow statuses per module â€” status vocabularies multiply (Submitted/Filed/Lodged/Sent all meaning the same thing); one canonical, documented status taxonomy per workflow keeps tags, filters, and reports coherent.
- Batch approve/reject without a check-your-answers-style confirmation step â€” irreversible bulk money decisions need an explicit confirm listing the affected claims, especially in an audit-chained system.

## RECOMMENDATIONS
- Build the Local Travel Reimbursement claim wizard as a GOV.UK task list per claim: sections like 'Trip details', 'Itinerary and expenses', 'Attachments', 'Certification' shown as tasks with statuses (Not yet started / In progress / Completed / Cannot start yet), and 'Check and submit' locked until all sections complete. This directly implements the CLAUDE.md rule 'GOV.UK task-list for checklists' and maps cleanly onto per-section draft rows.
- Split UX rules by audience in docs/standards/ui-standards.md: claimant flows (infrequent users) follow one-thing-per-page/few-things-per-page with a step indicator; approver and admin-console screens (daily expert users) use denser multi-field pages and tables, per GOV.UK's own guidance for regularly-used internal forms and the Home Office internal-service precedent.
- Add three shared components to the component inventory now, before the first form ships: ErrorSummary (role=alert, focus-on-render, anchors to fields, 'Error: ' page-title prefix, wording identical to inline errors), StatusTag (sentence case, token colors only, mapped to the semantic green/amber/red/grey scheme), and TaskList. Codify the canonical status taxonomy for reimb (Draft, Submitted, Under review, Returned for correction, Approved, Disbursed, Rejected) in the module doc so tags, queue filters and reports share one vocabulary.
- Implement save-and-return server-side: every wizard step POST persists to the claim's draft rows (status='draft', normal created/updated ownership columns, soft-delete rules apply); no separate 'save' concept needed since staff are already authenticated â€” show 'Last saved 14:32' feedback and surface 'Continue a saved claim' on the module landing page. This also satisfies WCAG 3.3.7 since nothing is ever re-entered.
- Pre-populate every claimant-identity field (name, position, salary grade, division, official station) from core_users/the staff directory as read-only display values with an 'update your details' escape hatch â€” WCAG 2.2 Redundant Entry compliance and it keeps HR data authoritative in one place.
- End the wizard with Check-your-answers (each row linking back to its step, server-computed totals only â€” reinforcing the no-client-side-money-math rule) and a Confirmation page showing the XX-YYYY-NNNN reference number, what happens next ('Your supervisor will review this claim'), expected timeframe, and a 'Download PDF copy' link.
- Generate official claim PDFs server-side in a Celery task using an HTML/CSS-to-PDF renderer (e.g. WeasyPrint, already Python/Docker-friendly) from templates matching the DOH paper reimbursement form layout: title block with bureau name, reference number, Manila-formatted timestamps via core/time.py, signature blocks, and full Q&A recap per the USWDS keep-a-record pattern. Store the PDF, record its SHA-256 in the hash-chained core_audit_logs, and mask any sensitive identifiers to last-4 on the printout. Record the chosen renderer in tech-stack.md (standing rule 9).
- Build the approver queue as a filterable, sortable, paginated table (MOJ patterns): filter panel for status/claimant/date-range/amount with removable applied-filter chips, sortable Submitted-date and Amount columns, visible result count, explicit empty state, and semantic status tags per row. Row click opens a full-page claim detail (never a modal) with a persistent summary strip (claimant, amount, status, ref) and a 'Back to queue' link that restores filter state.
- Render the claim detail's activity timeline directly from core_audit_logs entries (actor, action, Manila timestamp, remarks) â€” the hash-chained audit foundation becomes the user-facing document-status-tracking feature for both reimbursement and DMWIS, at near-zero extra cost.
- Adopt a WCAG 2.2 AA per-screen acceptance checklist in the QA gate: 24x24px minimum targets (relevant to dense approver tables â€” enforce via spacing tokens), focus never fully obscured by sticky headers/panels, no drag-only interactions (receipt reordering/upload must have button alternatives), consistent help placement (put a help/contact slot in the shared page layout template so 3.2.6 is satisfied structurally), and error-summary behavior on every form.
- Returned-for-correction flow: when an approver returns a claim, reopen it as a task list with the offending sections flagged 'There is a problem' (red tag) plus an error-summary-style box at the top quoting the approver's remarks and linking to each affected section â€” this reuses the error grammar users already learned from validation.
- Batch approval (if built) must show a confirmation page listing every affected claim and total amount before committing, and write one audit entry per claim â€” never a silent bulk mutation in an audit-chained government system.
- Record Philippine compliance posture in docs/standards/: DICT MC 004-2017 makes WCAG the binding national standard (target 2.2 AA to exceed it); E-Governance Act RA 12254 + its 2026 IRR covers internal systems (note its cybersecurity/interoperability mandates for the on-prem deployment); GWTD/NGA web template applies only to any future public-facing surface such as the landing shell or public CSS-IS survey links â€” internal screens stay on the token/component system.
- Feature-flag each new UI pattern rollout (queue redesigns, batch actions, PDF generation) fail-safe OFF per the existing flag discipline, so the approval chain never blocks on a half-shipped UI.
