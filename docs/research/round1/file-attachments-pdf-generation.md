# agent2
TOPIC: File attachments and server-generated documents in an internal claims app (Office-Connect: FastAPI/async SQLAlchemy/PostgreSQL 16/Celery, on-prem Windows Server, no cloud)

## KEY PRACTICES
- PRACTICE: Defense-in-depth upload validation: allowlist extensions AND allowlist MIME types AND verify magic bytes â€” never rely on any single check
  WHY: OWASP is explicit that every individual technique (extension check, Content-Type header, file signature) is bypassable on its own (double extensions like .jpg.php, spoofed headers, polyglot files); only the combination plus safe storage/serving is adequate.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- PRACTICE: Never trust the client-supplied Content-Type header; sniff the actual bytes server-side (python-magic/puremagic or explicit signature checks) after streaming to a temp file
  WHY: The Content-Type header is set by the client and is trivially spoofed; server-side content sniffing is the only version of the type check the server controls.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- PRACTICE: Generate a random/derived stored filename (UUID or content hash); keep the user's original filename only as DB metadata, length-capped and sanitized to a conservative character set
  WHY: Eliminates path traversal, shell metacharacter, double-extension, and duplicate-name attacks entirely â€” the filesystem never sees attacker-controlled text. The original name is still available for display and Content-Disposition.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- PRACTICE: Store uploads outside the web root on a dedicated non-executable volume, and serve them exclusively through an authenticated application endpoint â€” never via a static-files mount
  WHY: OWASP's storage preference order is: separate host, then outside webroot, then (last resort) inside webroot write-only. A Docker volume mounted only into the API container, with downloads flowing through an auth-checked route, gives you the 'outside webroot' guarantee and per-request RBAC.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- PRACTICE: Content-addressed on-disk layout: attachments/<tenant_id>/<yyyy>/<mm>/<sha256[:2]>/<sha256>, with sha256 + size + sniffed MIME stored on the attachment row
  WHY: Fan-out directories avoid huge flat folders (slow on NTFS); the hash gives free deduplication of re-uploaded receipts, integrity verification on every download, and a natural value to write into the hash-chained core_audit_logs for tamper evidence â€” exactly what a COA audit trail wants.
- PRACTICE: Re-encode every accepted image server-side with Pillow (decode â†’ resize cap â†’ save as JPEG/WebP), keep MAX_IMAGE_PIXELS enforced, treat DecompressionBombWarning as an error, and strip EXIF/XMP/ICC on save
  WHY: Re-encoding destroys embedded payloads in image files (OWASP calls this 'image rewriting'), MAX_IMAGE_PIXELS defends against pixel-flood decompression bombs, and stripping EXIF removes GPS coordinates of employees' homes from receipt photos â€” a real privacy issue in a government office.
  SOURCE: https://pillow.readthedocs.io/en/stable/handbook/security.html
- PRACTICE: Virus-scan asynchronously via clamd: run the official clamav/clamav container on the internal Docker network (TCP 3310, never published to the host), with a Celery task submitting files and a scan_status state machine (pending â†’ clean | infected | error)
  WHY: clamd holds signatures in RAM (needs roughly 1â€“3 GB and about a minute to warm up), so scanning belongs in a background worker, not the upload request path; a status column lets the API accept uploads instantly while withholding downloads until the file is clean.
  SOURCE: https://docs.clamav.net/manual/Installing/Docker.html
- PRACTICE: For the offline production Windows Server, maintain ClamAV signatures with cvdupdate: pull .cvd/.cdiff files on an internet-connected machine, transfer them to an internal HTTP mirror (nginx container), and point freshclam at it with ScriptedUpdates off
  WHY: cvdupdate is Cisco-Talos's official tool for exactly this air-gapped scenario; without a signature update path, an offline ClamAV decays into a false sense of security within weeks.
  SOURCE: https://github.com/Cisco-Talos/cvdupdate
- PRACTICE: Generate official forms with WeasyPrint (HTML/CSS â†’ PDF) rendered from Jinja2 templates inside a Celery worker; reserve ReportLab for pixel-exact coordinate drawing on replicas of pre-printed forms; do not adopt wkhtmltopdf
  WHY: WeasyPrint is pure-Python (pip-installable, no headless browser â€” important on an offline Windows/Docker host), has strong CSS 2.1+ paged-media support ideal for invoice/voucher-style documents, and lets the same design-token stylesheet discipline govern print output. wkhtmltopdf was archived in January 2023 with CSS frozen at an ancient WebKit â€” unmaintained software is a liability on a no-cloud government server. ReportLab is the fallback when a form must match a printed original to the millimeter.
  SOURCE: https://pdfbolt.com/blog/python-html-to-pdf-library
- PRACTICE: Serve downloads through one auth-checked endpoint (e.g. GET /api/v1/attachments/{id}/download) using FileResponse/StreamingResponse with async file IO, Content-Disposition: attachment with an RFC 5987-encoded sanitized filename, and X-Content-Type-Options: nosniff
  WHY: Streaming keeps memory constant for large PDFs, the authorization check runs on every request (no guessable static URLs), and attachment+nosniff prevents the browser from executing a disguised file in the app's origin â€” the standard mitigation for stored-XSS-via-upload.
  SOURCE: https://fastapi.tiangolo.com/advanced/custom-response/
- PRACTICE: Mobile receipt capture: use <input type="file" accept="image/*" capture="environment">, compress client-side (browser-image-compression or compressorjs, ~2048px long edge / ~80% quality), and handle iPhone HEIC by converting to JPEG (heic2any client-side or pillow-heif during the server re-encode)
  WHY: Modern phone photos are 4â€“12 MB; client-side compression makes uploads fast on office Wi-Fi and phones, and HEIC is Apple's default format that most browsers cannot display â€” unhandled, iPhone users (a large share of staff) get broken previews or rejected uploads.
  SOURCE: https://upsidelab.io/blog/handling-heic-on-the-web
- PRACTICE: Align retention with Philippine government schedules: financial/voucher records and their supporting documents carry roughly 10-year retention under the National Archives of the Philippines General Records Disposition Schedule, and COA's constitutional mandate (Art. IX-D Â§2) covers preservation of vouchers and supporting papers
  WHY: Reimbursement receipts are supporting documents to Disbursement Vouchers â€” they are auditable government financial records, so the app's soft-delete/purge design must guarantee bytes survive at least the GRDS period regardless of what users 'delete'. Verify exact per-record-type periods against the official GRDS before coding the purge job.
  SOURCE: https://www.respicio.ph/commentaries/data-retention-and-disposal-schedules-for-hr-and-finance-records-in-the-philippines
- PRACTICE: Treat generated PDFs as immutable snapshot attachments: store the rendered file with its sha256 in the attachment store, write the hash into the audit chain, and re-generate as a NEW version rather than overwriting when data changes
  WHY: An approved travel reimbursement form is an official record; if the PDF is re-rendered from live data later, the document a signatory saw can silently change. Snapshot-at-approval plus hash-in-audit-chain makes every issued document verifiable.
- PRACTICE: Enforce size limits at every layer: reverse-proxy body cap in production, streamed byte-count enforcement in the endpoint (reject mid-stream, don't buffer first), per-file and per-claim quotas in application config
  WHY: A single unchecked upload can fill the on-prem server's disk (no elastic cloud storage to absorb it); streaming enforcement means the server never materializes an oversized body in RAM or temp space.
  SOURCE: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html

## PITFALLS
- Trusting the client Content-Type header or the filename extension as the type check â€” both are attacker-controlled and are the #1 upload bypass OWASP documents (double extensions, spoofed MIME).
- Mounting the attachments directory with FastAPI StaticFiles (or any direct static link): every stored file becomes reachable without authorization, and one guessed/leaked URL exposes another employee's receipts.
- Accepting SVG as an 'image' format: SVG is XML that can carry scripts and is a classic stored-XSS vector when later served inline â€” restrict receipts to JPEG/PNG/WebP/PDF.
- Reading uploads fully into memory (await file.read()) or doing sync file IO / WeasyPrint rendering inside the async request handler â€” blocks the event loop; WeasyPrint can take seconds per document and belongs in Celery.
- Running the virus scan synchronously in the upload request: clamd needs ~1 min warm-up and 1â€“3 GB RAM, and a scanner outage would take uploads down with it. Conversely, failing OPEN (serving files whose scan never completed) quietly defeats scanning â€” withhold downloads while scan_status is pending/error.
- Letting ClamAV signatures go stale on the offline server because nobody owns the cvdupdate transfer ritual â€” an unscheduled manual process decays; make it a documented recurring operational task.
- Hard-deleting attachment bytes when a claim is soft-deleted, or letting a naive purge job honor deleted_at before the GRDS/COA retention window â€” receipts backing a Disbursement Voucher are government financial records for ~10 years; this would also violate standing rule 6.
- Choosing wkhtmltopdf for form generation: archived January 2023, frozen ancient WebKit, no flexbox, known SSRF-style risks with untrusted HTML â€” dead-end dependency for an on-prem system that must live for years.
- Windows/NTFS filename traps if any user-derived text ever reaches the filesystem: reserved device names (CON, PRN, NUL, COM1â€¦), trailing dots/spaces, case-insensitivity collisions, and the 260-char MAX_PATH limit. Hash-named storage sidesteps all of it â€” keep it that way.
- Ignoring HEIC: iPhones default to HEIC, most browsers can't render it, and generic magic-byte allowlists reject it â€” users see mysterious failures unless it is converted client- or server-side.
- Decompression bombs: a tiny PNG that expands to 20,000Ã—20,000 pixels can OOM the worker during thumbnailing â€” never set Pillow's MAX_IMAGE_PIXELS to None, and cap PDF page counts before rendering previews.
- Serving user PDFs inline in the app origin without nosniff/sandboxing: PDFs can contain JavaScript and embedded files; prefer Content-Disposition: attachment for originals, or render server-generated preview images for in-app display.
- Putting bearer tokens in download query strings as the primary auth: they leak into proxy logs and browser history; on a same-origin intranet app, cookie-based session auth on the download route (or short-lived single-use signed URLs) is safer.
- Storing file bytes in PostgreSQL (bytea/large objects) 'because it's transactional': bloats WAL/base backups and makes the 10-year archive unwieldy â€” keep bytes on the volume, metadata + hash in the DB, and make backup jobs cover both atomically enough (DB dump + volume snapshot in that order).

## RECOMMENDATIONS
- Build attachments as a shared service in core/ (module code imports core, never each other â€” rule: no cross-module imports) with a core_attachments table per database-standards: id BIGINT identity, tenant scoping, sha256 CHAR(64), size_bytes, original_filename, sniffed_mime, storage_key, scan_status (pending/clean/infected/error), full created_/updated_/deleted_ ownership columns. Link to owners via per-module join tables (e.g. reimb_claim_attachments) so FK naming stays clean and RBAC checks resolve through the owning entity.
- Upload pipeline (single code path for all modules): stream to a temp file in the attachments volume enforcing the size cap mid-stream â†’ sniff magic bytes against the allowlist (JPEG, PNG, WebP, PDF; convert HEIC) â†’ compute sha256 â†’ dedupe or move to attachments/<tenant>/<yyyy>/<mm>/<sha256[:2]>/<sha256> â†’ insert row (scan_status=pending) â†’ write sha256 into the hash-chained core_audit_logs â†’ enqueue Celery tasks: clamd scan, then image re-encode/EXIF strip/thumbnail for images.
- Fail-closed download gate: GET /api/v1/attachments/{id}/download checks (a) row not soft-deleted, (b) requester authorized on the owning claim/document via RBAC, (c) scan_status=clean â€” then streams with aiofiles, Content-Disposition: attachment (RFC 5987-encoded sanitized original name), X-Content-Type-Options: nosniff. Never add a StaticFiles mount over the volume. If ClamAV is down, files stay pending and undownloadable â€” this is the one place 'fail-safe OFF' means deny, and it should be documented in the module doc.
- Compose services: add clamav (official clamav/clamav image, TCPSocket 3310, internal network only, mem_limit ~3 GB, healthcheck on clamd PING) alongside the existing api/db/redis/worker. Dev on Docker/Windows ports scheme is unaffected since 3310 is never published to the host.
- Production offline signature plan (write into tech-stack.md + an ops runbook): a designated internet-connected PC runs cvdupdate on a schedule, produced .cvd/.cdiff files are transferred to the Windows Server, an internal nginx container serves them as a private mirror, freshclam in the clamav container points at it with ScriptedUpdates off. Name an owner and a cadence (weekly minimum); alert in the admin console when signature age exceeds a threshold.
- PDF generation for the reimbursement module's official outputs (Itinerary of Travel, Certificate of Travel Completed, Disbursement Voucher support, claim summary): WeasyPrint + Jinja2 in a Celery task, with a dedicated print stylesheet built from the same design tokens (A4, @page headers/footers, reference number XX-YYYY-NNNN and generation timestamp in Manila time on every page). All money figures come from server-computed values only â€” the template never does arithmetic. Store the output as an immutable attachment (hash in audit chain); regeneration after data change creates a new version row, never an overwrite.
- Record WeasyPrint's native-library needs (Pango/HarfBuzz etc.) in tech-stack.md â€” inside the Linux Docker image this is a couple of apt packages; avoid ever running it directly on Windows outside the container. If a form must overlay a scanned pre-printed government form pixel-perfectly, add ReportLab for that one template rather than fighting CSS.
- Receipt capture UX for the React frontend (later phase, spec it now in the module doc): <input accept="image/*" capture="environment"> for camera-first capture, browser-image-compression to ~2048px/0.8 quality before upload, progress + retry for flaky Wi-Fi, and server-side HEICâ†’JPEG via pillow-heif so old browsers still work when client conversion is unavailable. Server-side Pillow re-encode is mandatory regardless of what the client sends.
- Retention + soft-delete alignment: add retention_class and retain_until (timestamptz) to core_attachments; reimbursement receipts inherit ~10-year financial-records retention per the NAP General Records Disposition Schedule (verify the exact GRDS 2023 item numbers against the official issuance before implementation, and record the citation in docs/modules/). Soft delete (deleted_at/deleted_by) only hides; a Celery-beat disposal job may remove bytes only when retain_until has passed AND an admin has approved disposal, and even then the DB row and an audit-chain disposal entry remain permanently. The oc_app DB role's lack of DELETE already enforces half of this.
- Size/quota policy in config (never hardcoded, per-tenant configurable via the existing config system): e.g. 10 MB per image, 20 MB per PDF, ~15 attachments per claim, per-user daily quota; enforce in the streaming endpoint and again at the reverse proxy in production. Add a disk-free-space check to the admin console health panel â€” on-prem Windows Server has no elastic storage.
- Backups: document that a restore point = PostgreSQL dump + attachments volume snapshot taken together (DB first, then volume, so every row's file exists). Verify integrity on restore by re-hashing a sample of files against stored sha256 â€” the content-addressed layout makes this a cheap scheduled job and a strong story for COA/ISO audits.
- Sequencing suggestion: land the core attachment service (validation, hashed storage, auth-checked download, soft-delete/retention columns) in Phase 0/1 as foundation, feature-flag scan enforcement and PDF generation per module, and reuse the identical pipeline for DMWIS documents and CSS-IS exports later â€” this is precisely the kind of shared floor the phase plan intends.
