# agent9
## MISSING AREAS (gap critic)
- Notifications and on-prem email delivery: The digest repeatedly assumes notifications exist (SLA escalations, liquidation reminder ladders, event bus 'reimbursement approved -> notification') but never designs the delivery layer: an on-prem SMTP relay (office Exchange/postfix container, no cloud email APIs), a core notification service with templates, per-user preferences, digest vs immediate sends, an outbox table with retry/bounce handling, and an in-app notification center as fallback for staff without reliable mailboxes.
- Search: Nothing covers how users find things â€” claims by reference number/claimant, DMWIS documents by content, staff directory lookup. The plan should commit to PostgreSQL full-text search (tsvector/pg_trgm, which respects soft-delete and tenant filters and adds no new infrastructure) as the standard, and define when/if that ever escalates, plus how scanned-attachment text (OCR or none) is handled for DMWIS.
- Reporting and analytics architecture: Reports are a named module but the only mention is 'route report generation to Celery.' Missing: the read-model strategy (views/materialized views vs live queries against soft-deleted, workflow-versioned data), the specific government outputs (COA/DBM formats, monthly unliquidated-CA aging, per-division spend), export formats (XLSX for accounting), and how the Sec. 22 export caps from the compliance section reconcile with accounting's need for bulk data.
- Legacy data migration (CSS-IS and historical records): CSS-IS migration is a planned module yet there is zero migration methodology: source assessment, ETL with validation/reconciliation counts, how migrated rows get ownership/audit-chain columns (a documented 'migrated' actor and chain-genesis policy), ID mapping, cutover vs parallel-run decision, and whether historical paper travel claims are back-captured or the module starts clean.
- Reference-data and seed lifecycle management: Individual seeds are mentioned (permissions, EO 77 clusters, PSGC region map) but there is no unified strategy: idempotent, environment-aware seed framework; an owner and update cadence for externally maintained datasets (PSA revises PSGC quarterly; annual PH holiday proclamations needed for any working-day deadline logic); and a rule for distinguishing Alembic data migrations from re-runnable seeds.
- Performance baseline, capacity planning, and load testing: Nothing states expected scale (a few hundred users, spiky month-end/deadline load) or budgets: p95 latency targets, asyncpg pool sizing, pagination/indexing standards, Redis memory sizing, VM CPU/RAM/disk sizing for the Hyper-V host, and a simple pre-go-live load test (e.g., Locust) so 'fast enough' is verified rather than assumed on the shared on-prem box.
- Offline/downtime resilience and paper fallback: PH government offices face brownouts and LAN outages; the plan needs a documented degraded-mode: UPS/generator assumptions for the server, an official 'system unavailable' paper procedure with back-entry rules (COA deadlines don't pause for downtime), client-side draft protection against mid-form disconnects, and a stance that the app is online-only (no offline PWA) so expectations are explicit.
- Training, rollout, and change management: Entirely absent, and it is the top failure mode for government internal systems. Plan should include a pilot cohort (one division) with a defined parallel-paper period and exit criteria, role-based training (claimant vs approver vs accounting), quick-reference guides and in-app contextual help, named super-users per division, a support/feedback channel, and management sponsorship milestones per module go-live.
- API versioning and contract management: /api/v1 appears by convention only; there is no policy for what constitutes a breaking change, deprecation windows, when v2 would ever exist, or how the future React frontend consumes the contract (OpenAPI-generated typed client, schema-diff check in the QA gate). Cheap to codify now in an api-standards doc, painful to retrofit after the frontend lands.
- Application observability: structured logging and error tracking: Ops coverage stops at Docker log rotation and Uptime Kuma; missing are app-level standards: structured JSON logs with correlation/request IDs (tied to audit entries), a log policy that excludes personal data (mirroring the audit-payload rule), and a self-hosted error tracker (GlitchTip/Sentry OSS in the compose stack) so exceptions surface without cloud services.
- Celery/background-job operations: The plan leans heavily on Celery (scans, PDFs, reminders, escalations) but never covers job operability: retry/backoff and max-retry policies, dead-letter handling and a failed-jobs admin view, task idempotency conventions beyond the escalation case, beat-schedule single-instance guarantees, and worker/queue-depth monitoring on the one prod box.
- Environment strategy, CI, and test-data management: Only dev and prod exist in the plan; a staging/UAT environment on the VM (or second compose project) is needed for accounting/COA-facing sign-off before each phase gate, plus CI (once the remote is provisioned) running tests/lint-imports/alembic-single-head, and a DPA-driven rule that dev/staging use synthetic or anonymized data â€” never real employee records, which also interacts with the PIA.
- Secrets management: No coverage of how DB passwords, session-signing keys, SMTP credentials, and future LDAP service-account credentials are stored, rotated, and kept out of the repo on an on-prem Windows/Hyper-V setup â€” at minimum a documented .env/Docker-secrets convention, rotation procedure in the ops runbooks, and inclusion of secrets in the DR rebuild path.
- Electronic signature validity for official forms: PDFs are generated with 'signature blocks' but the plan never decides whether system approvals legally substitute for wet-ink signatures on DVs/IoTs under RA 8792 and COA's electronic-documents rules (e.g., COA Circular 2021-006 on digital signatures), or whether printed forms still get physically signed. This determines the print/scan/physical-tracking workflow and should be settled with the resident COA auditor before the module ships.
- Audit-log and data growth management over the 10-year horizon: The hash-chained core_audit_logs plus append-only workflow events will grow unbounded across a decade of mandated retention; plan for partitioning or scheduled chain checkpoints so verification stays fast, and define how chain verification performance and backup size are managed as the log reaches millions of rows.
