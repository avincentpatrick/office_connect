# agent3
TOPIC: Approval workflow / state-machine engine design for internal business apps (expense approval and document routing), tailored to Office-Connect's homegrown FastAPI + PostgreSQL foundation

## KEY PRACTICES
- PRACTICE: Model approvals as an explicit state machine stored as data: a states table plus a transitions table (from_state, to_state, action), never just a status column mutated by scattered if/else code.
  WHY: A transitions table makes the set of legal moves closed and queryable â€” the engine can answer 'what can happen next?' and reject anything else. Status-column-only designs let any code path write any status, which destroys audit integrity and makes adding modules (DMWIS after Reimbursement) a rewrite instead of new rows.
  SOURCE: https://exceptionnotfound.net/designing-a-workflow-engine-database-part-4-states-and-transitions/
- PRACTICE: Keep three concerns in separate tables: design-time workflow definitions, runtime instance state, and append-only history. Never mix them in one table.
  WHY: Mixing definition, runtime, and history makes the engine brittle: config edits corrupt running items, and history rows get updated in place. Separation lets definitions be versioned, instances be small and hot, and history be immutable.
  SOURCE: https://letmepost.dev/blog/approval-workflows
- PRACTICE: Attach guard conditions to transitions so the same action from the same state can route differently (e.g. 'approve' goes to division-chief review only if amount > threshold). Guards are preconditions evaluated at execution time; only the transition whose guard passes fires.
  WHY: Guards move routing rules (amount thresholds, document completeness) out of handler code and into declarative, per-transition data â€” the core mechanism that makes approval chains configurable per tenant without code changes.
  SOURCE: https://statecharts.dev/glossary/guard.html
- PRACTICE: Make who-can-act-when a property of the transition, enforced server-side at execution time: each transition row declares the required role/position, and the API recomputes the allowed-actions set (state x actor x guards) on every POST â€” the UI only renders what that same endpoint returns.
  WHY: Hiding buttons client-side is not authorization. A single server-side 'available transitions for this user on this instance' function used by both GET (render) and POST (validate) guarantees the UI and the enforcement can never disagree.
- PRACTICE: Distinguish 'Reject' (terminal, no resubmission) from 'Return/Request change' (loop back to requester, resubmission expected), as Dynamics 365 workflow actions do. Track a revision number, require a reason comment, and keep every prior decision in history across resubmissions.
  WHY: Collapsing both into one 'rejected' state forces users to file brand-new requests, orphaning history and reference numbers. An explicit returned_for_correction state preserves the item's identity and full decision trail across correction loops â€” essential for government audit.
  SOURCE: https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/fin-ops/organization-administration/workflow-actions
- PRACTICE: Handle delegation/OIC via a time-boxed delegation table and record actions as 'on behalf of': the event stores both the actual actor and the person/position whose authority was exercised; accountability stays with the original owner.
  WHY: Philippine government offices rotate Officers-in-Charge constantly. Without first-class delegation, offices resort to password sharing or items stall for weeks. Recording the real approver alongside the delegator is what Oracle/Workday-class systems do to keep the audit trail truthful.
  SOURCE: https://fingate.stanford.edu/authority/delegate-or-share-oracle-approval-worklist
- PRACTICE: Implement escalation/SLA as data plus a periodic sweep: stamp sla_due_at (UTC) on each step at activation, and model escalations like BPMN non-interrupting timer boundary events â€” notify/escalate in parallel while the original task stays open; reserve interrupting (auto-reroute/auto-reject) timers for explicit policy.
  WHY: Camunda's situation patterns show escalation as a parallel nudge (possibly recurring, e.g. every 2 hours) rather than stealing the task, which matches how offices actually work: the approver is reminded, then their chief is notified, but the item is not silently rerouted.
  SOURCE: https://docs.camunda.io/docs/components/best-practices/modeling/modeling-with-situation-patterns/
- PRACTICE: Design step records so sequential and parallel approvals share one shape: one row per approval step with a sequence number and a join type (all-of / any-of / n-of-m), rather than a single current_approver column on the instance. The four-eyes (two independent reviewers in parallel) pattern is the canonical parallel case.
  WHY: A lone current_approver column hard-codes sequential-only forever. Per-step rows cost nothing now and make parallel review purely additive later (new join_type value), with fan-in decided by counting completed step rows in one locked transaction.
  SOURCE: https://docs.camunda.io/docs/components/concepts/workflow-patterns/
- PRACTICE: Keep workflow history as an immutable append-only event log (who, what, from_state, to_state, when, on-behalf-of, comment, payload) and treat the denormalized current_state on the instance as a derived read-model, per the event sourcing pattern.
  WHY: The append-only event sequence is the authoritative audit record: any past state of a claim can be reconstructed, disputes are resolvable, and nothing can be quietly edited. The mutable summary exists only for query speed.
  SOURCE: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
- PRACTICE: Make every transition idempotent and concurrency-safe: compare-and-swap on the expected state (UPDATE ... WHERE id=:id AND current_state=:expected â€” zero rows means someone acted first, return 409), SELECT FOR UPDATE for parallel fan-in, and a client-supplied idempotency key with a unique constraint so retries/double-clicks replay the original result instead of acting twice.
  WHY: Two approvers acting at once, a double-clicked Approve button, and Celery's at-least-once delivery are all certainties, not edge cases. State-conditioned writes plus persisted idempotency keys are the standard defense; disabling the button is UX polish, not correctness.
  SOURCE: https://algomaster.io/learn/system-design/idempotency
- PRACTICE: Store approval chains as versioned configuration with immutable published versions: editing a chain creates a new version; each instance is pinned to the definition version it started under and completes on it (Camunda's default), with explicit migration as a separate deliberate operation if ever needed.
  WHY: In-flight items must never silently reroute because an admin edited the chain. Version-pinning is how every mature engine (Camunda process versioning, Temporal workflow versioning/determinism) protects running instances from definition changes.
  SOURCE: https://docs.camunda.org/manual/latest/user-guide/process-engine/process-versioning/
- PRACTICE: Assign approval steps to roles/positions, not user IDs, in definitions; resolve to concrete people at step activation and re-verify authority at action time.
  WHY: Staff turnover, leave, and OIC rotations are constant in government offices. Chains keyed to 'Division Chief' keep working across personnel changes; chains keyed to a person break the moment they transfer, and re-verifying at action time closes the gap where someone lost the role after assignment.
- PRACTICE: Treat any change to transition semantics as a versioned deployment, echoing Temporal's determinism rule: code/config that decides what happens next must produce the same decision for the same history, so behavioral changes require a new version rather than an in-place edit.
  WHY: Temporal's entire versioning apparatus exists because changing decision logic under running executions causes non-deterministic breakage. Even without adopting Temporal, the lesson transfers directly to a homegrown engine: old items replay/resume under old rules.
  SOURCE: https://docs.temporal.io/develop/go/workflows/versioning

## PITFALLS
- Status-column-only design: any code path can write any status, invalid jumps (draft -> paid) are possible, and 'what can this user do now?' is answered by duplicated if/else in every endpoint.
- Editing workflow definition rows in place: in-flight claims silently reroute or crash when an admin tweaks the chain; without immutable versions there is also no answer to 'which rules applied when this was approved?' during an audit.
- Lost-update races: two approvers (or one approver plus an escalation job) act simultaneously and last-write-wins produces a double approval or a skipped step; plain 'read state, check, write state' without compare-and-swap or row locking is broken under async concurrency.
- Non-idempotent action endpoints: a double-click or HTTP retry records two approval events; without a persisted idempotency key the second request cannot be distinguished from a genuine second action.
- Authorization enforced only by hiding UI buttons â€” a crafted API call approves a claim the actor should never touch; the transition check must run server-side on every execution.
- Approvers hardcoded by user ID: chains break on resignation, transfer, leave, or OIC designation; the item stalls with no one able to act and no lawful reassignment path.
- Delegation done by password sharing or silent reassignment: the audit trail shows the wrong human acting, which in a government office is a genuine liability (COA findings).
- Overwriting or deleting history on return-for-correction/resubmission: prior decisions vanish, and conflating 'rejected' with 'returned' forces new requests and orphans reference numbers.
- Escalation timers that double-fire: Celery is at-least-once, so a sweep that emails/escalates without first checking (and atomically recording) that the step is still pending and not yet escalated will spam and double-route.
- SLA deadlines computed with naive datetimes or Manila-local storage â€” violates the project's own ensure_aware()/UTC rule and produces off-by-8-hour escalations; also beware business-day vs calendar-day SLA math.
- Building a free-form expression language for guards on day one: an unbounded DSL becomes an unauditable security surface; typed columns (min_amount, required_role) cover the reimbursement module's real rules.
- Engine coupled to module tables (workflow code importing reimb_ models): breaks the no-cross-module-import rule and makes DMWIS/CSS-IS adoption impossible; the engine must live in core with modules referencing it, never the reverse.
- Enum drift between Python state enums and DB state rows: code and data disagree about what states exist; one source of truth (DB lookup rows, validated at startup) is needed.
- Turning off a feature flag with items mid-flight and having undefined behavior: flags must gate creation of new instances only â€” in-flight items always get to finish.

## RECOMMENDATIONS
- Build the engine in core (importable by reimb/dmwis/css/admin, never the reverse), following your DB standards: core_workflow_definitions, core_workflow_definition_versions (immutable once published), core_workflow_states, core_workflow_transitions, core_workflow_steps (per-instance step rows), core_workflow_instances, core_workflow_events (append-only, created_* only â€” your documented log exception), core_workflow_delegations. reimb_claims carries workflow_instance_id FK; the engine never knows module tables.
- core_workflow_transitions columns: definition_version_id, from_state_id, to_state_id, action (approve/return/reject/cancel/escalate/resubmit), required_role_id (or position), min_amount/max_amount numeric(12,2) guards, requires_comment boolean (force reasons on return/reject). Resist a JSONB rules DSL until a real requirement appears â€” typed columns are auditable and indexable.
- Execute every transition in one async SQLAlchemy transaction: (1) idempotency-key check via unique index on (workflow_instance_id, idempotency_key) â€” on conflict return the original event; (2) compare-and-swap UPDATE core_workflow_instances SET current_state_id=:new, row_version=row_version+1 WHERE id=:id AND current_state_id=:expected â€” zero rows updated returns HTTP 409; (3) INSERT the core_workflow_events row; (4) append the hash-chained core_audit_logs entry. Use SELECT FOR UPDATE on step rows for parallel fan-in counting.
- Expose GET /claims/{id}/actions returning the computed allowed-transitions set for the current user (state x role x guards x delegation), and have POST /claims/{id}/actions/{action} validate through the exact same function. The React UI renders only what GET returns and never computes permissions itself.
- Pin every instance to workflow_definition_version_id at creation; in-flight items complete under their pinned version even after the admin console publishes a new chain. Publishing = insert new version rows + flip is_published; never UPDATE a published version (consistent with your soft-delete/no-hard-delete rules). Admin edits to a draft version are free; publish is one-way.
- Return-for-correction: add returned_to_requester state and a revision_no on the instance, incremented on resubmit. Default policy: resubmission restarts the chain from step 1 (cleanest for COA audit â€” every approver saw the final version), with a per-definition-version flag to allow resume-from-returned-step later. All prior decisions stay in core_workflow_events across revisions.
- Delegation/OIC: core_workflow_delegations(delegator_user_id, delegate_user_id, scope: definition or all, starts_at, ends_at, reason, plus full ownership columns). Action authorization passes if actor is the resolved assignee OR holds an active (now between starts_at/ends_at, not soft-deleted) delegation. Events store actor_user_id AND on_behalf_of_user_id; UI renders 'Approved by Cruz (OIC for Reyes)'. Assign steps to roles/positions in definitions; resolve to people at step activation; re-verify at action time.
- Escalation/SLA: stamp sla_due_at timestamptz (UTC, via core/time.py) on each step at activation from a per-step sla_hours column in the definition version. A Celery beat sweep (every 5-15 min) selects pending steps past due and emits reminder/escalation events â€” idempotently: insert the escalation event with a unique (step_id, escalation_level) constraint so at-least-once delivery cannot double-fire. Escalations are ordinary events in the same log, and step SLA status maps directly to your semantic amber/red UI colors.
- Ship the Local Travel Reimbursement chain as sequential (steps with sequence_no, join_type='all' with one assignee) but keep join_type (all/any/quorum) on core_workflow_steps from day one so four-eyes parallel review for DMWIS is a data change, not a migration.
- Make the DB the single source of truth for states: no Python state Enum that can drift. Load states/transitions for the pinned definition version at runtime; add a startup validation (and a test) that every definition version's transition graph is connected, has exactly one initial state, and every non-terminal state has an exit.
- Write a property-style test that replays core_workflow_events and asserts the folded state equals core_workflow_instances.current_state_id for every instance â€” cheap continuous proof that the event log and read-model never diverge, and a natural companion to your hash-chain verification.
- Feature-flag semantics for workflows: a flag OFF blocks creating NEW instances of a definition but never blocks acting on in-flight ones. Document this in the module doc and standards, since it interacts with rule 'flags fail-safe OFF'.
- Record deltas in docs/modules/local-travel-reimbursement.md as usual (reference specs use singular names â€” your workflow tables are new, but any spec-referenced status names should be mapped to your state rows there), and add the engine's schema decisions to database-standards.md if you adopt the append-only events exception pattern for it.
