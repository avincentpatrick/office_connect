# agent6
TOPIC: Operating a Dockerized FastAPI + PostgreSQL app on an on-prem Windows Server (no cloud): container substrate, backups, monitoring, safe updates, intranet HTTPS, service supervision, and DR runbooks

## KEY PRACTICES
- PRACTICE: Run Linux containers inside a Hyper-V Linux VM (Ubuntu LTS/Debian) with native Docker Engine + Compose â€” never directly on Windows Server. Windows Server acts purely as the hypervisor.
  WHY: Linux containers share the host kernel, so they cannot run natively on Windows Server. Microsoft's support policy only covers Windows Server containers (via Mirantis Container Runtime), and the LCOW feature is deprecated â€” Docker 23.0 removed it entirely. A Hyper-V Linux VM gives you the boring, fully-supported mainstream path: systemd-managed Docker Engine, native ext4 volumes, standard docs apply verbatim.
  SOURCE: https://learn.microsoft.com/en-us/troubleshoot/windows-server/containers/support-for-windows-containers-docker-on-premises-scenarios
- PRACTICE: Do not use Docker Desktop on the production server. It targets Windows 10/11 developer workstations, and Docker's subscription agreement explicitly requires government entities to hold a paid subscription regardless of size.
  WHY: A DOH bureau is a government entity: running unlicensed Docker Desktop is a compliance liability on top of the technical mismatch (Desktop assumes an interactive user session and auto-updates). Docker Engine inside a Linux VM is free (Apache-2.0) and has no such terms.
  SOURCE: https://www.docker.com/legal/docker-subscription-service-agreement/
- PRACTICE: Avoid WSL2 as the production substrate. If ever forced into it, wrap startup in a Task Scheduler job or NSSM service â€” but treat that as a stopgap, not the design.
  WHY: Microsoft has never published a production-support statement for WSL2 on Windows Server; boot-time autostart of a compose stack requires community workarounds (scheduled tasks with highest privileges, NSSM wrappers, systemd-in-WSL hacks) that break across WSL updates. A Hyper-V VM's 'Automatic Start Action' does the same job natively and survives unattended reboots.
  SOURCE: https://github.com/microsoft/WSL/discussions/14261
- PRACTICE: Backups: start with nightly pg_dump -Fc (custom format, compressed, selective-restore capable) while the database is small; graduate to pgBackRest (weekly full base backup + continuous WAL archiving) when the office needs point-in-time recovery or an RPO under 24 hours.
  WHY: Crunchy Data's guidance: pg_dump is a utility for specific database tasks and is fine early; production disaster recovery is best served by combining base backups with WAL archival (pgBackRest), balancing recovery speed, storage, and I/O overhead. pg_basebackup alone gives single point-in-time physical copies with no incrementals.
  SOURCE: https://www.crunchydata.com/blog/introduction-to-postgres-backups
- PRACTICE: Follow 3-2-1 for backup placement: the dump lands on a mounted backup volume in the VM, a scheduled job copies it off the VM to the Windows host or a NAS/second machine, and a periodic copy goes offline/off-site (even an external disk in a different room/building).
  WHY: On-prem with no cloud, the server itself is the single point of failure â€” fire, theft, ransomware, or a dead RAID controller takes the 'backups' with it if they only live on the same box. Off-box and offline copies are the only mitigation available without cloud storage.
- PRACTICE: Run proven-restore drills on a schedule (quarterly at minimum): restore the latest backup into a throwaway Postgres container, run a verification script, and record the drill date and outcome in the runbook.
  WHY: An untested backup is a hope, not a backup. DR guidance is consistent: test restore procedures at least twice a year, and write them so a competent substitute â€” someone who knows the tech but not this system â€” can execute them alone. Silent backup corruption and forgotten passwords/paths are only discovered by drilling.
  SOURCE: https://www.pdq.com/blog/disaster-recovery-plan-template-with-free-downloads/
- PRACTICE: Configure Docker log rotation explicitly (daemon.json: json-file driver with max-size + max-file); rotation is OFF by default (max-size defaults to unlimited).
  WHY: Docker's own docs confirm the json-file driver does not rotate by default. On a static on-prem box, unbounded container logs are one of the most common causes of disk-full incidents, and a full disk crashes PostgreSQL â€” turning a logging oversight into a database outage.
  SOURCE: https://docs.docker.com/engine/logging/drivers/json-file/
- PRACTICE: Monitoring sized for a small IT shop: a real /health endpoint in the app (checks DB + Redis), Docker Compose healthchecks + restart policies on every service, and a lightweight self-hosted monitor (Uptime Kuma, ~100 MB RAM) running on a DIFFERENT machine than the app VM, alerting via email/messaging webhook. Add disk-space and certificate-expiry checks.
  WHY: A Prometheus/Grafana stack is overkill and un-maintainable for 1-2 IT staff; Uptime Kuma covers HTTP checks, cert-expiry warnings, and notifications at a fraction of the footprint. The monitor must live outside the thing it monitors or it dies with it. Disk space is the top silent killer on fixed-capacity on-prem hardware.
  SOURCE: https://betterstack.com/community/guides/monitoring/uptime-kuma-guide/
- PRACTICE: Run Alembic migrations as an explicit, separate deploy step (docker compose run --rm api alembic upgrade head) inside a maintenance window â€” not in the FastAPI startup/lifespan hook.
  WHY: Migration-on-boot races when multiple workers/replicas start (each tries to migrate), can hang the ASGI startup, and couples 'app restarts' to 'schema changes' so a crash-loop can re-trigger DDL. Community consensus for production is a discrete migration step that completes before the app comes up; for an internal office app, a short announced maintenance window replaces blue-green entirely.
- PRACTICE: Make every deploy rollback-capable: version-tagged images (never :latest), keep the previous image locally, take a pre-update pg_dump immediately before migrating, and prefer expand/contract (backward-compatible) migrations so the previous app version still runs against the new schema.
  WHY: With no blue-green and no cloud, the rollback path IS the previous image tag plus the pre-update backup. If a migration is destructive and the new code is broken, only that pre-update dump gets you back inside the maintenance window.
- PRACTICE: Intranet HTTPS via an internal CA whose root is centrally distributed: if the office has an AD domain, use Active Directory Certificate Services (root auto-trusted on all domain-joined PCs via Group Policy) and load the issued cert into a reverse proxy (Caddy or nginx) in the compose stack. Caddy's 'tls internal' self-managed CA is the fallback when no AD CS exists â€” but its root must then be pushed to every client by GPO or manually.
  WHY: Caddy's docs are explicit that with internal CAs 'it is the system administrator's responsibility to ensure Caddy's root CA is properly added to the necessary trust stores.' In a Windows-centric government office, GPO distribution of a root cert is the one mechanism that scales to every staff PC without touching each machine; certs that browsers don't trust train users to click through warnings.
  SOURCE: https://caddyserver.com/docs/automatic-https
- PRACTICE: Unattended-boot chain with zero custom supervision code: Hyper-V VM 'Automatic Start Action' = always start (with delay) â†’ systemd starts Docker Engine (enabled) â†’ Docker applies 'restart: unless-stopped' to every container. Test the full chain by power-cycling the host.
  WHY: Each link is a built-in, supported feature of its layer â€” no NSSM, no scheduled-task scripts, no logged-in session required. This is what makes the Hyper-V-VM approach decisively better than WSL2 for a server that must survive Windows Update reboots with nobody in the office.
- PRACTICE: Write per-scenario DR runbooks (DB restore, full server rebuild from bare metal, disk full, cert renewal/expiry, stack won't start after reboot), each with an owner, last-tested date, pre-checks, numbered steps, verification, and rollback. Keep a printed copy and a copy on the backup target â€” never only on the server they describe.
  WHY: With limited IT staff, the person who built the system may be unavailable during the incident; runbooks written at 'competent substitute' detail level are the institution's memory. A runbook stored solely on the dead server is worthless precisely when needed.
  SOURCE: https://www.pdq.com/blog/disaster-recovery-plan-template-with-free-downloads/

## PITFALLS
- Assuming the dev setup (Docker Desktop / WSL2 on Windows) carries over to the production Windows Server â€” LCOW is removed from Docker 23+, Docker Desktop requires a paid subscription for government entities, and WSL2 autostart-at-boot relies on fragile community hacks.
- Backing up by file-copying the live PGDATA directory or snapshotting the Docker volume while Postgres runs â€” produces inconsistent, often unrestorable copies; only pg_dump/pg_basebackup/pgBackRest produce valid backups of a running cluster.
- Backups that exist but were never restore-tested â€” corruption, wrong pg_dump format flags, or missing roles/extensions surface only during the real disaster.
- All backup copies living on the same physical box (or inside the same VM) as the database â€” fire, ransomware, or hardware failure destroys data and 'backups' together.
- Running Alembic migrations in the FastAPI startup hook with multiple Uvicorn workers â€” concurrent upgrade races, hung startups, and crash-loops that re-run DDL; a failed boot-migration leaves the app half-up with no clear operator signal.
- No Docker log rotation (the default!) plus no disk-space alerting â€” the disk silently fills over months, then PostgreSQL crashes and possibly corrupts; disk-full is the classic on-prem slow-motion outage.
- Windows Update rebooting the host at 3 a.m. without Hyper-V auto-start configured â€” the app stays down until staff notice the next morning; always power-cycle-test the full boot chain.
- Storing PGDATA on a Windows-mounted path (drvfs/9p/virtiofs bind mount from the host) instead of the Linux VM's native filesystem â€” known source of Postgres corruption and severe I/O degradation; keep volumes on ext4 inside the VM.
- Deploying with :latest tags or auto-updaters (Watchtower) â€” non-reproducible state, surprise breakage outside maintenance windows, and no known-good tag to roll back to.
- Publishing PostgreSQL (5432) and Redis (6380/6379) to the office LAN â€” only the reverse proxy's 443 should be reachable; databases stay on the compose-internal network.
- Letting an untrusted/self-signed cert ship 'temporarily' â€” staff learn to click through browser warnings, which defeats HTTPS and is a habit that is very hard to un-train in a government office.
- Internal CA or server certificate expiring with no renewal reminder â€” intranet certs are typically 1-2 years and nobody is watching; monitor expiry (Uptime Kuma does this) and calendar the renewal.
- Host antivirus scanning the VM's virtual disk or backup files during the backup window â€” massive I/O slowdowns; add exclusions per vendor guidance.
- DR documentation, the git repo, and the Alembic migration history existing only on the production server â€” a bare-metal rebuild needs all three, so the git remote must live on separate hardware.

## RECOMMENDATIONS
- Production topology: Windows Server runs only Hyper-V; create one Ubuntu 24.04 LTS VM ('oc-prod') with Docker Engine + Compose plugin. Set the VM's Automatic Start Action to 'Always start' with a startup delay, enable Docker in systemd, and give every compose service 'restart: unless-stopped'. Verify by power-cycling the host before go-live. Record the VM, OS, and Docker Engine versions in docs/standards/tech-stack.md (standing rule 9).
- Keep the dev port scheme (8001/5432/6380) dev-only. In production, expose only 443 from a Caddy (or nginx) container; Postgres and Redis live on the compose-internal network with no published ports. Document this delta between dev and prod compose files in the module/ops docs.
- Write /etc/docker/daemon.json in the VM before first deploy: {"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"5"}} â€” Docker does not rotate logs by default. Also enable Postgres logging_collector with size/age-based rotation.
- Add a real /api/v1/health endpoint (cheap SELECT 1 + Redis PING, no auth, never cached) alongside the existing never-500 /api/v1/config. Wire compose healthchecks to it for the API and pg_isready/redis-cli ping for the databases. Run Uptime Kuma on a different machine (the Windows host itself, or the IT staff PC acting as monitor) with checks on /health, disk space (via a small agent or scheduled-task script), and TLS cert expiry; alert to the office email/group chat.
- Backup regime for launch: nightly cron in the VM runs 'docker compose exec -T db pg_dump -Fc -U oc_app_owner office_connect > /backups/oc-YYYYMMDD.dump'; a Windows scheduled task copies /backups off the VM to the host, and a weekly job copies to a second machine or external disk stored separately. Retention: 14 daily / 8 weekly / 12 monthly (align final retention with the office's government records-retention rules). Declared RPO: 24h, RTO: 4h â€” get management sign-off. Before the Local Travel Reimbursement module goes live with real claims, upgrade to pgBackRest (weekly full + WAL archiving) if a sub-24h RPO is demanded.
- Quarterly restore drill with a distinctive Office-Connect twist: restore the latest dump into a throwaway container, run 'alembic current' to confirm schema head, then run the hash-chain verification over core_audit_logs â€” the audit chain you already built doubles as a free end-to-end backup-integrity check (a truncated or corrupted restore breaks the chain). Log each drill's date/operator/outcome in the ops runbook.
- Codify the update procedure as a script + runbook: (1) announce maintenance window (internal app â€” evenings/weekends are fine, no blue-green needed); (2) pre-update pg_dump; (3) pull/build version-tagged image oc-api:X.Y.Z (never :latest), keep the previous tag; (4) compose stop api workers; (5) 'docker compose run --rm api alembic upgrade head' as an explicit step â€” never in the FastAPI lifespan; (6) compose up; (7) smoke test /health and /api/v1/config; (8) rollback = previous image tag + pre-update dump. Prefer expand/contract migrations so the N-1 image runs against the new schema.
- HTTPS: if BLHSD/DOH workstations are AD domain-joined, request a cert from AD CS (or stand up the AD CS role) for an internal DNS name like office-connect.<office-domain> and mount it into Caddy â€” the root is already GPO-trusted on every staff PC. If there is no AD CS, use Caddy 'tls internal' and distribute Caddy's root CA cert via GPO (or scripted install) to all client machines. Either way: HTTP only 301-redirects to HTTPS, and Uptime Kuma watches cert expiry. Never let staff normalize clicking through certificate warnings.
- Create docs/operations/ mirroring your per-module docs discipline (standing rule 8): one runbook per scenario â€” restore-database.md, rebuild-server-from-scratch.md, disk-full.md, certificate-renewal.md, stack-down-after-reboot.md â€” each with owner, last-tested date, pre-checks, numbered steps a competent substitute can follow, verification, and rollback. Keep a printed binder copy and a copy on the backup target machine, not only in the repo on the prod server.
- Provision the git remote NOW (your own rule says before Phase 0 closes) on hardware other than the future production server â€” the repo with its Alembic migration history is a DR artifact: the rebuild-from-scratch runbook is 'clone repo â†’ build images â†’ restore dump â†’ alembic verify', and that only works if the repo survives the server.
- When the ops stack is chosen (Ubuntu VM, Docker Engine, Caddy, Uptime Kuma, later pgBackRest), record each in docs/standards/tech-stack.md with version and rationale per standing rule 9, and note the prod-vs-dev substrate difference (Hyper-V Linux VM vs Docker-on-Windows dev) prominently â€” it is the single most surprising fact for whoever inherits this system.
